I reviewed the full intermediate report and then source-checked the important paths in current upstream Linux, including USB runtime PM, reset-resume/rebind, `usb_queue_reset_device()`, URB anchors, the Bluetooth errno conversions, and BlueZ’s MGMT-status handling.

One correction to my interim note above: **the report is right about BT-18.** I initially followed the *system-resume* `usb_resume()` path too far. Runtime resume instead goes through `usb_runtime_resume()` → `usb_resume_both()` directly. If `reset_resume` is required and the interface driver lacks that callback, `usb_resume_interface()` sets `needs_binding`, but the runtime path does **not** run the system-resume `unbind_marked_interfaces()` / later `usb_resume_complete()` rebind sequence. Thus the interface can indeed remain bound but logically marked for rebind after a successful runtime reset-resume. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/driver.c)

The important findings, using the report's requested severity scheme:

1. **[Patch 2/B — blocker — source-checked] `pm_runtime_active()` cannot be used as the synchronization primitive the patch assumes.** The kernel documentation directly says its result can only be trusted while holding `dev->power.lock`, or while otherwise guaranteeing that runtime-PM enablement/status cannot change. More subtly, it returns true not only for `RPM_ACTIVE` but also whenever `disable_depth != 0`. [GitHub](https://github.com/torvalds/linux/blob/master/include/linux/pm_runtime.h) That makes the current `BTUSB_SUSPENDING && !pm_runtime_active()` test a snapshot/TOCTOU test. It can observe `RPM_ACTIVE`, then an autosuspend can enter `RPM_SUSPENDING` before `usb_autopm_get_interface()`. The latter is `pm_runtime_resume_and_get()`, and synchronous `rpm_resume()` explicitly waits when another suspend/resume operation is underway. So the exact thing B promises to avoid—blocking behind PM—remains possible. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/base/power/runtime.c) A much better primitive is the atomic “get only if already active” operation, `pm_runtime_get_if_active()`: check ACTIVE under the PM lock and acquire the usage reference in the same operation. Even better, if BT-18 gets fixed first, I think B can probably become conceptually simpler: while `BTUSB_SUSPENDING` is set, **do not initiate the HCI timeout reset at all**. The special “ACTIVE but btusb never resumed” exception exists largely because the broken runtime reset-resume path currently uses the timeout reset as an accidental recovery mechanism.

2. **[Patch 2/B — should-fix — source-checked] The report's “active reset-resume” exception is real, but it should not become permanent policy.** The USB core sets `needs_binding` when reset-resume is required but the interface has no `reset_resume`; system resume later unbinds/rebinds such interfaces, whereas runtime resume lacks that later phase. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/driver.c) Consequently, B has to allow the old reset after the interface becomes active only because that reset happens to force the missing rebind. Once BT-18 has a proper fix, retaining this exception makes B more complicated and preserves a race for no good reason. I would therefore solve BT-18 first, then write B against the corrected invariant. That argues for changing the current A/B/D/E ordering or combining the logically dependent pieces.

3. **[Patch 3/D — blocker — source-checked] The queued work itself is lifetime-safe; the *policy* is the problem.** `usb_queue_reset_device()` retains an interface reference, and its worker calls `usb_lock_device_for_reset()`. That routine refuses the reset if the USB device is gone/suspended or the interface has entered UNBINDING/UNBOUND, and it serializes against the USB-device lock. So I do **not** see the feared UAF/disconnect race here. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/usb.c) Likewise, because USB PM holds the appropriate device serialization while callbacks execute, the queued worker cannot simply nest another reset halfway through the current reset-resume callback. The runtime mechanics are sensible.

4. **[Patch 3/D — blocker — source-checked + architectural reasoning] Registering `btusb_reset_resume()` globally is much broader than BT-18 and temporarily claims that ordinary `btusb_resume()` is sufficient after a USB reset.** The USB core's existing behavior when a driver has no `reset_resume` is deliberately conservative: mark it for unbind/reprobe. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/driver.c) D instead runs ordinary `btusb_resume()`, which restarts traffic and plays deferred URBs, and only *afterward* schedules another USB reset to provoke the rebind. There is therefore a real interval in which HCI traffic can be replayed against a controller which has just suffered a USB reset but has not gone through btusb probe/setup again. Your emulator says that works for its emulated controller; that is not enough to establish it for every Realtek, Intel, QCA, MediaTek, etc. device using btusb. This is, to me, a stronger objection than the workqueue lifetime question.

5. **[Patch 3/D — blocker — source-checked] The system-resume side effect is too large to send untested.** D changes behavior for every btusb device that legitimately gets reset-resume during system sleep, then queues a *second* USB reset. The core already has a system-sleep mechanism specifically designed to unbind marked interfaces and rebind them in the PM `complete` phase; rebind is deliberately delayed while `is_prepared` is set. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/driver.c) I would not post D upstream before actual suspend/resume testing on at least the laptop plus a Realtek device affected by `BTUSB_WAKEUP_AUTOSUSPEND`. My preference is indeed to investigate a **USB-core fix for the missing runtime rebind**, but I would not naïvely call `rebind_marked_interfaces()` inline from `usb_runtime_resume()`: runtime resume of the parent can itself have been initiated from the child interface's PM-resume stack, so a synchronous reprobe there deserves careful USB-core review. A deferred core rebind mechanism looks conceptually cleaner.

6. **[Patch 1/A — nit/should-fix — source-checked] Ignoring `-EACCES` is defensible, but the comment is too categorical.** Runtime-PM helpers return `-EACCES` whenever runtime PM is disabled; system sleep is an important reason but not the only possible reason. [GitHub](https://github.com/torvalds/linux/blob/master/Documentation/power/runtime_pm.rst) I would either log `-EACCES` at debug level or word the comment as “expected while runtime PM is disabled, notably during system sleep.” For other errors, an error-level diagnostic is justified because deferred HCI traffic cannot be delivered. A rate-limited error would be slightly safer against a persistent PM failure. I do not see a correctness reason to hold A.

7. **[Patch 4/E — ready — source-checked] I think this patch is correct.** `usb_anchor_urb()` itself only takes the anchor spinlock and manipulates references/list state; it does not sleep. Kernel USB code already uses it from spinlocked paths. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/urb.c) More importantly, E gives exactly the serialization wanted: either the sender acquires `txlock` first and places the URB in `deferred`, after which `play_deferred()` must see it, or resume gets `txlock` first, drains/clears `BTUSB_SUSPENDING`, after which the sender takes the normal direct-submit path. There is no longer a state in which the sender has decided “defer” but has not yet made the URB visible to the resume side. I found no contrary anchor→`txlock` locking path that would make this an obvious inversion, and your lockdep run adds useful evidence. **E is the patch I would be most comfortable sending independently now.**

8. **[Patch 5/C — should-fix before even RFC-as-fix — reasoning from evidence] One incident is not enough to assign the QCA9377/Ryzen/root-hub combination a permanent autosuspend quirk.** The workaround is rational—it prevents entering exactly the power transition that preceded BT-17—but the experiment has not established that autosuspend caused the controller's physical non-responsiveness. The emulator explicitly cannot reproduce the AMD xHCI/electrical/firmware cause; it reproduces what software does *after* the controller fails. I would keep C out of the A/B/D/E series. A standalone RFC saying “one machine, one occurrence, proposed mitigation, requesting reports/testing” would not be unreasonable, but I personally would wait for the deciding recurrence with USB-core/xHCI debug or a controlled A/B demonstration. Otherwise reviewers can fairly say this merely hides an unexplained hardware/firmware failure.

9. **[CO-44 — should-fix — source-checked] `-ETIMEDOUT → MGMT_STATUS_TIMEOUT` is correct, but there is a complementary bug in the same conversion that I would fix at the same time.** The Bluetooth core's canonical conversion is unambiguous: HCI status `0x05` (Authentication Failure) becomes `EACCES`; HCI `0x08` (Connection Timeout) becomes `ETIMEDOUT`; and the reverse conversion maps `-EACCES → 0x05` and `-ETIMEDOUT → 0x08`. [GitHub](https://github.com/torvalds/linux/blob/master/net/bluetooth/lib.c) Yet `mgmt_errno_status()` currently maps `-ETIMEDOUT` to `MGMT_STATUS_AUTH_FAILED` and has **no `-EACCES` case at all**. So the 2022 sync conversion created a two-sided distortion: genuine timeout → authentication failure, while genuine authentication failure can fall through to generic failure. I would change the patch to add both mappings:
   `-EACCES → MGMT_STATUS_AUTH_FAILED` and `-ETIMEDOUT → MGMT_STATUS_TIMEOUT`, with one test for each. That makes the fix considerably harder to argue against.

10. **[CO-44 — should-fix — source/history checked] `Fixes: 161510ccf91c` is exactly the right origin.** That commit introduced `mgmt_errno_status()` and specifically introduced the `-ETIMEDOUT → AUTH_FAILED` mapping while converting these MGMT paths to the synchronous HCI-command infrastructure. I found no sensible BlueZ dependency on “a timed-out kernel command must appear as 0x05”; quite the opposite, BlueZ already has separate semantics for `MGMT_STATUS_TIMEOUT`, including an authentication-timeout result in pairing code. [GitHub](https://github.com/pauloborges/bluez/blob/master/src/device.c) I consider this **stable-worthy**, especially if you make the correction symmetric with `-EACCES`, because this is an incorrect externally visible status rather than cosmetic logging. Because it changes a userspace-visible status, I would mention that fact explicitly in the commit message rather than hide it.

### Series structure I would use

I would **not send the current five CO-43 patches as one series yet**. E is independently convincing and can stand alone. A also stands alone after its small wording/logging cleanup. B and D are really two halves of one recovery problem and should be redesigned together; B currently preserves an unsafe exception specifically because D/the USB core has not yet fixed BT-18.

For BT-18, I would first take the finding to USB maintainers: “successful **runtime** reset-resume + interface driver without `reset_resume` sets `needs_binding`, but unlike system resume there is no subsequent unbind/rebind.” The source really does show that asymmetry. [GitHub](https://github.com/torvalds/linux/blob/master/drivers/usb/core/driver.c) If that is judged intentional, then btusb needs its own delayed-reprobe solution; if it is judged a USB-core omission, fixing it there removes most of the ugliness from B and D.

C should remain separate from all of those because it is a **root-cause avoidance quirk**, whereas A/B/D/E concern generic correctness once resume fails.

### Tests I would add before sending B/D

The biggest missing test is real system suspend/resume. After that I would specifically test disconnect/unbind while D's queued reset is pending; a multi-interface btusb device with primary + isoc and active SCO; failure of URB resubmission inside `btusb_resume()`; repeated PM cycling around the exact B decision to expose ACTIVE→SUSPENDING TOCTOU; system-suspend abort while `btusb_waker()` has received `-EACCES`; and a real controller whose state genuinely changes on USB reset rather than the emulator's scripted “healthy after reset” behavior. KCSAN would also be worthwhile for B/E—the current KASAN+lockdep configuration is excellent for lifetime/locking defects but does not establish that an unlocked PM-state snapshot is logically stable.

For the emulator specifically, the remaining blind spots matter: vhci does not reproduce the AMD xHCI port-reset/SET_ADDRESS implementation, electrical port state, firmware power loss, or a device that remains physically refractory until VBUS/power removal. And the system-freezer limitation means D's most dangerous newly affected path is exactly the path the emulator cannot validate.

**My ranking after this review is therefore: E is ready; A is essentially ready; CO-44 is very close but should become a two-sided errno mapping fix; B needs rewriting; D needs redesign/USB-core discussion; C needs more hardware evidence.**

The two findings I would send back to the maintainer immediately are **the documented invalidity of the unlocked `pm_runtime_active()` decision in B**, and **the missing `-EACCES → MGMT_STATUS_AUTH_FAILED` half of CO-44**. Those are concrete source-level issues rather than matters of taste.
