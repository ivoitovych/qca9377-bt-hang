## 1. Why the mapping is what it is

**Origin, the earliest version.** The table, with the `-ETIMEDOUT` entry, first appears in `[RFC 3/5] Bluetooth: hci_sync: Make use of hci_cmd_sync_queue set 1` (2021-05-27).
- URL: https://lore.kernel.org/linux-bluetooth/20210528000136.52352-3-luiz.dentz@gmail.com/
- Query: `git grep -n -E 'ETIMEDOUT|mgmt_errno_status|AUTH_FAILED' 32654735f -- m` → `518:+	case -ETIMEDOUT:` / `519:+		return MGMT_STATUS_AUTH_FAILED;`
- The 2021-05-20 version (`[PATCH 2/2] … Make use of hci_cmd_sync_queue`, Message-ID `20210520164213.1381518-2-luiz.dentz@gmail.com`) has no such table. The same `git grep` on `5b1ed89cd` finds nothing.

**The only review comment on error conversion** came from Marcel Holtmann on that 2021-05-20 version (https://lore.kernel.org/linux-bluetooth/F97186B5-BC6D-48F9-A07C-3E128C5E5CB4@holtmann.org/):
- Marcel: "Either we use u8 as return value or we convert it to the matching errno value."
- Luiz's reply (https://lore.kernel.org/linux-bluetooth/CABBYNZ+ujvaxwiPzfgNxOZi9phVUdi8dNtCJSa4WUq=gjzNncQ@mail.gmail.com/): "it looks like the mgmt can actually report the status".
- So the errno→MGMT table was a by-product of that choice. **No one commented on the `-ETIMEDOUT` entry itself.**

**Versions RFC, v1–v8, 2021-05-27 to 2021-10-27.** Every version carries the entry unchanged.
- Query: `git log master --until=2021-09-02 -G'mgmt_errno_status|MGMT_STATUS_AUTH_FAILED'` → only the patch mails themselves (RFC 3/5, v1 3/5, v2 3/5, v3 3/6, v4 3/7, plus neighbour artefacts).
- Applied version v8 02/23: https://lore.kernel.org/linux-bluetooth/20211027235900.1882863-3-luiz.dentz@gmail.com/ (`git grep -A1 ETIMEDOUT 0eadce3f8 -- m` shows the same lines in v5).
- There is no human reply to any "set 1" patch. Subject search `--grep='hci_cmd_sync_queue set 1'` → only `[PATCH vN …]` mails.
- The only human reply to the v8 cover letter is Marcel's: "all 23 patches have been applied to bluetooth-next tree." (https://lore.kernel.org/linux-bluetooth/4633683C-42A0-47AE-94B1-9938CD5BCE82@holtmann.org/).

**Later commits to `mgmt_errno_status()`.** Two since 2021, neither touching `-ETIMEDOUT`.
- Queries:
  - `git log --oneline -L '/^static u8 mgmt_errno_status/,/^}/:net/bluetooth/mgmt.c' v6.12` → only `161510ccf91c9` (and `ca69b7957bf2e`, the old `mgmt_status()`);
  - the same on `bluetooth-next/master` and `bluetooth/master` from `v7.0`;
  - the function text at `v6.12` is identical to `v7.0`'s.
- `c0bb764fc0826` "Bluetooth: mgmt: reply to cancelled mgmt commands instead of silently dropping" (Shuai Zhang, applied 2026-10-14) adds `-ECANCELED → MGMT_STATUS_CANCELLED`. It has no `Fixes:` and no `Cc: stable`.
- `65683fbed5c83` (`bluetooth/master`) = `7eac806143005` (`bluetooth-next/master`), "Bluetooth: MGMT: Return RFKILLED for Set Powered on a blocked controller" (Tobias Wilken, 2026-10-21, applied 2026-10-23).
  - It adds `-ERFKILL → MGMT_STATUS_RFKILLED`.
  - Trailers: `Fixes: cf75ad8b41d2`, **no `Cc: stable`**.
  - It is the closest template for CO-44 (see §5 and §6).
- `git log -G 'ETIMEDOUT|AUTH_FAILED|mgmt_errno_status' 161510ccf91c..v6.12 -- net/bluetooth/mgmt.c net/bluetooth/mgmt_util.c net/bluetooth/hci_sync.c` → three unrelated commits (`7453847fb22c7`, `45340097ce6ea`, `b62e72200eaad`), none of them in this function.

**Did anyone propose changing the entry?** No, from 2021-05 to 2026-11-13.
- lore subjects: `--grep='mgmt_errno|mgmt_status|AUTH_FAILED|Authentication Failed|ETIMEDOUT|MGMT_STATUS|status code|errno'` (`-i -E`).
  - Hits: `Bluetooth: Use bt_status to convert from errno` (Luiz, 2022). That converts errno to an *HCI* status (`bt_status()`), not `mgmt_errno_status()`.
  - Unrelated `errno.h` patches.
- lore full text: `-G'mgmt_errno_status'`. Hits are only the 2021 series, Shuai Zhang's `-ECANCELED` threads (2026-07/08) and the RFKILLED thread (2026-10).
  - Luiz's replies in the `-ECANCELED` thread (`3758f4547`, `a2938d445`) discuss `HCI_AUTO_OFF` and a review finding. Nothing about the timeout entry.
- lore full text: `-G'^[+-]?\s*return MGMT_STATUS_(TIMEOUT|AUTH_FAILED);'` → only the 2021 series.
- lore full text: `-i -G'(auth(entication)?[ _]failed.{0,60}(time ?out|timed out|ETIMEDOUT|-110))|((time ?out|timed out|ETIMEDOUT).{0,60}auth(entication)?[ _]failed)'` → nothing.

## 4. Userland consumers of 0x05 vs 0x08

**BlueZ programs that open `HCI_CHANNEL_CONTROL` or `mgmt_new_default()`.**
- Query: `grep -rln -E 'mgmt_new_default\(|HCI_CHANNEL_CONTROL' --include=*.c`.
- Result: bluetoothd (`src/adapter.c`, `src/shared/mgmt.c`, `src/shared/gap.c`), btmgmt (`client/mgmt.c`), the mesh daemon (`mesh/mesh-mgmt.c`, `mesh/mesh-io-mgmt.c`), btmon (`monitor/control.c`), `peripheral/gap.c`, `tools/btconfig.c`, `advtest.c`, `oobtest.c`, `isotest.c`, and the testers.

**How they branch.** Query: `grep -rn -E '(status|err) *[!=]= *(MGMT_STATUS_[A-Z_]+|0x0?[58])\b|case MGMT_STATUS_'` over `client mesh src peripheral plugins profiles` and those tools.
- btmgmt, mesh, `shared/gap`, `peripheral`, `adv_monitor`: only `!= MGMT_STATUS_SUCCESS`. Mesh also tests `NOT_SUPPORTED`/`UNKNOWN_COMMAND` on feature reads (`mesh/mesh-mgmt.c:65`). They print `mgmt_errstr()`, so **only the text changes** ("Timeout" instead of "Authentication Failed").
- btmon only decodes the status for display.
- bluetoothd mode/power replies: `property_set_mode_complete()` (`src/adapter.c:3176-3205`) branches only on `MGMT_STATUS_RFKILLED`. Any other status gives D-Bus `org.bluez.Error.Failed` with message `mgmt_errstr(status)`. **The D-Bus error name is unchanged; its message text goes from "Authentication Failed" to "Timeout".**

**Every BlueZ comparison with `MGMT_STATUS_AUTH_FAILED` or `MGMT_STATUS_TIMEOUT`.** Query: `grep -rn -E 'MGMT_STATUS_AUTH_FAILED|MGMT_STATUS_TIMEOUT' --include=*.c --include=*.h`.

| Site | What reaches it | Kernel source of that status | Changed by CO-44? |
|---|---|---|---|
| `src/adapter.c:8933` `bonding_attempt_complete()`: PIN retry on `AUTH_FAILED` | Pair Device reply (`pair_device_complete()`, 8960-8993), `MGMT_EV_AUTH_FAILED` (`auth_failed_callback()`, 9175-9187), `MGMT_EV_CONNECT_FAILED` (10249), plus the constant `DISCONNECTED` (9106) | see below | no |
| `src/device.c:7552` `device_bonding_complete()`: disconnect on `AUTH_FAILED` | `bonding_complete()` ← the above; `device_bonding_attempt_retry()` (7745) reuses `bonding->status` | same | no |
| `src/device.c:2092` `bonding_status == AUTH_FAILED` → `ERR_BREDR_CONN_KEY_MISSING` | `bonding_status` is set only at `device.c:7551` (`grep -n bonding_status`) | same | no |
| `src/device.c:3528` `new_authentication_return()`: `TIMEOUT` → `.AuthenticationTimeout` | `device_bonding_failed()` from the bonding paths and `connect_failed_callback()` (10258); `reply_pending_requests()` passes a constant | same | no |
| `src/shared/mgmt.c:189` `request_timeout()` | **produces** `MGMT_STATUS_TIMEOUT` itself when the kernel does not reply in time (BlueZ `faad125c5` "shared/mgmt: Add request timeout handling", 2022-01-24) | userland | — (BlueZ already uses 0x08 for "no answer") |
| `tools/mgmt-tester.c` seven `AUTH_FAILED` expectations, one `TIMEOUT` (2501, our new case) | pairing rejects; Set Device Class | — | only ours, as intended (CO-44 README) |

**Kernel side of the pairing statuses** (`bluetooth-next/master` `net/bluetooth/mgmt.c`). Every entry point takes a `u8`. `mgmt_status(int err)` sends only `err < 0` to `mgmt_errno_status()` (lines 314-320), so these statuses always go through the HCI table. **The pairing paths are unchanged: confirmed.**
- `pairing_complete_cb(struct hci_conn *conn, u8 status)` (3658) and `le_pairing_complete_cb(…, u8 status)` (3674);
- `mgmt_auth_failed(struct hci_conn *conn, u8 hci_status)` (10465);
- `mgmt_connect_failed(…, u8 status)` (10313);
- `pair_device()`'s immediate errors map `PTR_ERR` to explicit constants (3769-3779).

How the callers were checked:
- `git grep -n -E 'hci_connect_cfm\(|mgmt_auth_failed\(|mgmt_connect_failed\(' bluetooth-next/master -- net/bluetooth/`: every caller passes an HCI status or `bt_status(err)`.
- The one negative caller, `hci_conn.c:2298` `hci_connect_cfm(conn, err)`, is the BIG (ISO broadcast) path, not a pairing.
- An LE pairing connect that times out arrives as `hci_conn_failed(conn, bt_status(err))` (`hci_sync.c:7823`). `bt_status(-ETIMEDOUT)` returns `0x08` (`lib.c:197-198`), and the table maps that to `MGMT_STATUS_TIMEOUT`.
- **So the pairing path already reports a timeout as 0x08.** Only the errno path says 0x05.

**BlueZ's own documentation** (`doc/btmon-mgmt.rst:428-439`) defines the two statuses:
- 0x05 "Pairing or authentication procedure failed";
- 0x08 "Operation timed out".

**Third-party consumers.** Each file was fetched and checked with `grep -n -i -E 'status|0x05|0x08|…'`. None branches on 0x05, so none is affected.
- **Qt** `qtconnectivity/src/bluetooth/bluez/bluetoothmanagement.cpp` (dev): opens `HCI_CHANNEL_CONTROL` (line 137) and only parses `DeviceFoundEvent`. It never sends a command.
- **python-btsocket** (`ukBaz/python-btsocket`): `btmgmt_protocol.py` decodes the status to names (`AuthenticationFailed = 0x05`, `Timeout = 0x08`). `btmgmt_sync.py:34` raises on any `!= Success` with `status.name`, so only the name changes.
- **bleno** (`abandonware/bleno/lib/hci-socket/mgmt.js`): sends only `MGMT_OP_LOAD_LONG_TERM_KEYS`; `onSocketData()` only logs.
- **Android Bluetooth HAL** `net_bluetooth_mgmt.cpp` (page fetched): sends only Read Index List and never reads the status.
- **paypal/gatt** `linux/socket/socket.go`: only defines `HCI_CHANNEL_CONTROL = 3`.

## 5. Stable

**`stable-kernel-rules.rst`** (`bluetooth-next/master`) has no rule about fixes that change a user-visible value. The relevant lines:
- "It must either fix a real bug that bothers people";
- "No "trivial" fixes without benefit for users";
- it also says the versions are derived from `Fixes:` ("such tagging is unnecessary if the stable team can derive the appropriate versions from Fixes: tags");
- and `Cc: <stable+noautosel@kernel.org> # reason` exists for opting out.

**Bluetooth precedents for MGMT status-code fixes.** Query: `git log -i --all-match --grep='stable@' --grep='status' bluetooth-next/master ^v7.0 -- net/bluetooth/`, plus the same on `v6.12 -- net/bluetooth/mgmt.c`.

## What this changes for the patch

- **Commit message.**
  - Add the internal inconsistency, which is verified:
    - the pairing path already reports a timed-out connection as `MGMT_STATUS_TIMEOUT`: `bt_status(-ETIMEDOUT)` = 0x08, then the HCI table;
    - only the errno path says Authentication Failed.
  - The RFKILLED commit is a proven template: the symptom as btmon and bluetoothd print it before and after, then the one-line mapping, then `Fixes:`. It was accepted in 2 days.
  - Optional: a `Link:` to lore row 5 (QCA6390) or row 6 (Archie Pusaka's 2022 BlueZ patch, which names the timeout). They are the only lore-hosted user cases.
- **Below the `---`:**
  - say the mgmt-tester case is sent to BlueZ separately, give its subject, and add the lore link once it exists;
  - give the measured mgmt-tester totals;
  - say a user-visible status changes, and that no BlueZ code branches on 0x05 for these commands (only text changes). The pairing paths are untouched.
  - Optionally name one or two of the user reports.
  - Don't say 0x05 and 0x08 are interchangeable to user space in general: bluetoothd's bonding code does branch on `AUTH_FAILED` (§4).
- **Cc.** For `Cc: stable` (the operator's call):
  - in favour: this maintainer took two MGMT status fixes with `Cc: stable` within the last two months (`86ef0f58bdec`, `4728474344793`), and the user reports show the wrong status misleads diagnosis ("bothers people");
  - against: the two `mgmt_errno_status()` additions went in without it.

  Either form is accepted. Recipients otherwise as `kernel-send-package.md` §2 (`get_maintainer.pl`).
- **Tests.** Send the BlueZ mgmt-tester case the same day as the kernel patch:
  - its body names the kernel fix by subject;
  - below `---`, it links the kernel patch on lore and says it needs it;
  - expect a CheckPatch "Unknown commit id" warning if the body cites `161510ccf91c`.

  The maintainer applies the two together. The README note "send it only after the kernel patch has landed" can be relaxed to "the maintainer applies it after the kernel fix".
