## 2. CO-04, wording and the cancel path
- **Message** (`CO-04/patch/0001-...patch`, also `msg-co04.txt`): "only completes the request, as before" is replaced by: on -ECANCELED the callback only completes the request and no longer clears HCI_MESH_SENDING, which stays set until mesh_next() decides under hdev->lock; that is harmless in `hci_cmd_sync_clear()` because HCI_UNREGISTER is already set, `hci_cmd_sync_queue()` then refuses new work (`hci_sync.c:735`, -ENODEV) and the flag is read only by `mesh_send()` and `mesh_send_done()`, which `mgmt_index_removed()` cancels [source: `hci_core.c:2784-2816`, `hci_sync.c:320, 735`, M-4 in `docs/issues.md`]; in `send_cancel()` the hand-over follows the dequeue under the held lock.
- **Comment at the hand-over** reworded: "A transmission that is already on air was completed above, but its mesh_send_done() work is still pending and ends the air time and hands over when it runs." The old text claimed `mesh_send_done_sync()` hands over "a cancelled transmission".
- **Reviewer 7's case, A on air, B queued, cancel A** (research mesh-tester "Mesh - Send queue - cancel active", legacy and "- Ext Adv"; `CO-04/logs/active-*.log`, `extract-active.py`; 5 boots per kernel, `-s cancel`) [measured]: on bluetooth-next and on bluetooth-next + CO-04 alike, in all 20 case instances request 1 starts and is cancelled, request 2 never gets a start (`started2=0`) and gets its Mesh Packet Complete when request 1's air time ends (+82 to +102 ms). Confirmed from the source: `send_cancel()` completes the on-air request (removing it from `hdev->mesh_pending`), and `mesh_send_done_sync()` then completes `mgmt_mesh_next()`, which is now request 2 [source `mgmt.c` send_cancel/mesh_send_done_sync, unchanged by CO-04]. The research case itself fails on both kernels for its own tear-down count expectation; the evidence is the missing start.
- **Decision: reword, no fix here.** A clean fix needs to know which request is on air (a field in `struct mgmt_mesh_tx` or on `hdev`), to end the air time when it is cancelled (cancel `mesh_send_done`, disable advertising) and to hand over at once; that is a design change to the cancel semantics and the completion timing a client sees, more than a few lines [inferred]. Left as a separate item for the operator; CO-04 only states the behaviour as "not changed here" in its notes (20 of 20 runs each).

## 3. CO-04, reviewer 2's audit (read only, plus a KCSAN run)
- `mesh_send_start_complete(-ECANCELED)` from `hci_cmd_sync_clear()` calls `mesh_send_complete()` -> `mgmt_mesh_remove()` (list_del + free of a `mgmt_mesh_tx`) without `hdev->lock`, while `hci_cmd_sync_clear()` holds `cmd_sync_work_lock` [source]. At unregister `hci_unregister_dev()` sets HCI_UNREGISTER, drops the device from `hci_dev_list` (`hci_core.c:2788`) and only then calls `hci_cmd_sync_clear()` (`:2805`) [source].
  - Concurrent with MGMT mesh operations? New lookups fail after the list_del, and `hci_cmd_sync_queue()` refuses after HCI_UNREGISTER. A Mesh Send that already holds a device reference (MGMT commands use `hci_dev_get()`, not the SRCU read side that `hci_unregister_dev()` waits on at `:2792`; SRCU is used only in the ioctl path, `hci_core.c:553`) can still run `mgmt_mesh_add()` under `hdev->lock` while the `-ECANCELED` completion list_del's another entry without it: a window exists in principle [source, inferred]. It was not hit: 80 boots with KCSAN (UnregSweep and unregister sets, 20 each on the tip and on tip + CO-04) gave no report naming mesh, advertising or mgmt_pending code (`CO-04/kcsan-unreg-count.txt`, 2 to 6 boots had other reports) [measured]. The same code ran before CO-04: the unlocked free is pre-existing.
- `mesh_send_done_sync()` reads `list_empty(&hdev->adv_instances)` before taking `hdev->lock` [source]: an unlocked read of the advertising list, concurrent with Add Advertising at any time, not only at unregister. It is the same class as CO-05's subject (mesh path and the advertising list without the lock); CO-05 does not cover this site. Pre-existing, benign as a read in practice [inferred].
- **Relation to CO-14 (M-4) and M-5** (`docs/issues.md`): M-4 is the other half of removal: requests still pending (not started) are neither completed nor freed at removal, so they leak with their socket reference; CO-14's fix frees them in `mgmt_index_removed()` under `hdev->lock`. The unlocked `-ECANCELED` free is the one request whose start is queued; both sit on the same list and the same path, so the audit result is: an unlocked list_del here and a locked free there would be consistent if the `-ECANCELED` completion also ran under `hdev->lock`, which it cannot while `cmd_sync_work_lock` is held (M-5, the lock order). M-5 is removed by CO-04 (no destroy callback calls `mesh_next()` any more); the `-ECANCELED` completion remains the one place that takes no `hdev->lock` by design (stated in CO-04's message). A way to close it is to defer that completion to work that takes the lock (CO-14 territory) [inferred].
