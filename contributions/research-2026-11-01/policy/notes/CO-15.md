  2026-10-13; every pick until 01:06:58 was the laptop output, because the `default-nodes`

  the source; "by design". Parked: the proposal must be opt-in and the operator decides it.

## 2. WirePlumber 0.4.17 (Ubuntu) against master `4ab992fa2931` (= tag 0.5.19, 2026-10-30)

- [source] 0.4.17 `modules/module-default-nodes.c:262` `find_best_media_class_node()`:
  configured default `+20000*(N_PREV_CONFIGS+1)` (l.298), stack position i `+(16-i)*20000`
  (l.306) on top of `priority.session`. A new device gets nothing for being new.
- [source] master: the same rule, in Lua hooks:
  - `src/scripts/default-nodes/find-selected-default-node.lua:55`: the configured default
    scores `30000 + priority`;
  - `src/scripts/default-nodes/state-default-nodes.lua:47`: a stored node scores
    `20001 - i` ("the position in the stack alone decides", l.45-46; `481ecffb`, #1005,
    first in 0.5.18);
  - `src/scripts/default-nodes/find-best-default-node.lua:38`: the priority-based search is
    skipped once a node above 15000 is selected, so any available stored node beats any
    never-chosen node;
  - `src/scripts/lib/node-utils.lua:89-96` (`85556f15`, first in 0.5.17): among unstored
    nodes of equal `priority.session`, the **older** device (lower `object.serial`) wins.
    The opposite of "new wins".
- [source] Settings in master `src/config/wireplumber.conf:957-1143`: `device.restore-profile`,
  `device.restore-routes`, `linking.follow-default-target`, `node.restore-default-targets`,
  `node.stream.restore-target`, and the Bluetooth autoswitch ones. **None makes a newly
  connected device the default.** `node.restore-default-targets=false` (l.1138; `state-default-nodes.lua:179-195`
  removes the hooks) drops the
  whole history (then `priority.session` and, on ties, the older device decide).
- [source] `git rev-list --count 0.4.17..origin/master -- src/scripts/default-nodes`: 33
  commits; none adds such a rule. `0.5.18..0.5.19`: 34 commits; none touches default-nodes.
- [quoted] GitLab (API, `web/gitlab/`): no issue or MR since 2026-10-13 proposes it.
  #1036 (https://gitlab.freedesktop.org/pipewire/wireplumber/-/issues/1036, closed
  2026-10-09), maintainer julian: "When the current default goes away, it falls back to the
  most recent one in that list that's still available", and the fix offered there is to
  re-order the history by selecting devices in the wanted order. #914 (open, no maintainer
  reply), #352 (closed 2022, "changed this behaviour back and forth").
- **So 0.5 does not already do what CO-15 wants.** "Upgrade" is not the answer.

## 3. What exists today, on Ubuntu 24.04, without any upstream change

### a) PipeWire's `module-switch-on-connect` (shipped in 1.0.5, commented out)

- [source] `/usr/share/pipewire/pipewire-pulse.conf:65` (installed 1.0.5-1ubuntu3.3):
  `#{ cmd = "load-module" args = "module-switch-on-connect" }`.
- [source] 1.0.5 `src/modules/module-protocol-pulse/modules/module-switch-on-connect.c`:
  - acts only on sinks/sources added after its start (l.84, the `started` flag set at
    l.165 after the initial sync, l.197);
  - skips internal (`pci`/`isa` bus) devices except HDMI sinks (l.112-118);
  - skips node names matching `blocklist` (regex, default `hdmi`; l.32, l.121, l.257-263);
  - writes `default.configured.audio.sink`/`.source` (l.140; master l.148), which
    WirePlumber 0.4.17 stores in the stack as a selection (U11 entry, [source] note of
    2026-10-13).
  Master is the same (`pulse-module-switch-on-connect.c:31-34`, `:110-129`).
- [inferred from source] With
  `blocklist=hdmi|^alsa_|^bluez_input` it switches the **output only, Bluetooth only**:
  USB ALSA devices (`alsa_*`) and Bluetooth microphones (`bluez_input.*`) are skipped, internal
  devices are skipped by the bus rule. That removes two of the draft's objections ("switches
  inputs together with outputs"; U11 Next 3 "every new non-internal device ... inputs
  included").
- What remains different from the draft's idea [inferred]: each connection is written as a
  user selection, so it reorders the stack (when the headset leaves, the fallback is the
  previously chosen device still present, e.g. another headset, then the laptop);
  `only_from_unavailable` is not implemented (l.30, l.269-271). A profile switch re-creates
  the node; whether that re-adds it as "new" was not tested.
- The drop-in, for the operator's local test (PipeWire 1.0.5 merges arrays in drop-ins:
  `doc/dox/config/pipewire.conf.5.md:41-45` at `1.0.5`, "array sections are appended to"):
  `~/.config/pipewire/pipewire-pulse.conf.d/90-switch-on-connect.conf`
  ```
  pulse.cmd = [
      { cmd = "load-module" args = "module-switch-on-connect blocklist=hdmi|^alsa_|^bluez_input" }
  ]
  ```
  then `systemctl --user restart pipewire-pulse` (or log out and in). Untested here (no
  backslash needed: every Bluetooth input node name starts with `bluez_input`). To check:
  `pactl list modules short` shows the module with its argument; WirePlumber's journal shows
  `default.configured.audio.sink` changing at the next headset connection. Undo: rename the
  file to `.off` and restart pipewire-pulse.

### b) No configuration: order the history once

- [source] 0.4.17 l.298-306 and master `state-default-nodes.lua:47`: the most recently
  selected available device wins. Selecting the laptop output once, then each headset in
  turn (the most wanted last) puts every headset above the laptop; from then on a headset that
  connects while only the laptop output is present becomes the default. It breaks again
  whenever the laptop output is chosen by hand. This is the maintainers' own advice in #1036.
