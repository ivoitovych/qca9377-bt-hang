## 1. Why btusb has no `reset_resume`, and its history

**Finding: the absence is deliberate. Three btusb-side people have said a btusb reset-resume
cannot restore Bluetooth state, and that re-enumeration (unbind + probe) is the intended recovery.**

| when | what | evidence |
|---|---|---|
| 2013-05 | Shuah Khan *adds* `.reset_resume = btusb_resume`, to silence a warning | `502f769662978` "Bluetooth: Add missing reset_resume dev_pm_ops" |
| 2013-09 | Hans de Goede **reverts** it (Cc stable): HID-proxy devices reset into HID mode | `b1a8014471b01`: *"let the usb-system re-enumerate the device, and re-run the udev rules"* |
| 2013-10 | Alan Stern demotes the core's warning to `dev_dbg` | `0a56b4fa6844f`: *"the reset-resume method is optional"* |
| 2014-03 | Oliver Neukum posts an optional btusb `reset_resume` (refuses if HCI running) | https://www.mail-archive.com/linux-usb@vger.kernel.org/msg39199.html: *"it makes little sense to support reset_resume() in btusb"*. Not merged (`git log --all --grep`) |
| 2015-06 | Laura Abbott, "[PATCH 2/2] Bluetooth: btusb: Add reset_resume function" (calls `btusb_resume()` then re-runs setup) | https://lkml.iu.edu/hypermail/linux/kernel/1506.0/00749.html. Marcel Holtmann: *"even trying to replay any of it is just a lost cause"* (https://lkml.iu.edu/hypermail/linux/kernel/1506.0/00763.html). Oliver Neukum: *"Yes, but what is the point?"* (…/1506.0/00904.html). Not merged |
| 2017-11 | Alan Stern: the real fix is drivers with proper reset-resume; Oliver Neukum on btusb | https://lkml.iu.edu/hypermail/linux/kernel/1711.2/02710.html: *"Very hard to do with btusb."* / *"The connection is messed up if we lose power."* |

**Realtek, `udev->reset_resume = 1`:** the rebind *was* the intent, to reload firmware.
- `04b8c8143d464` (Daniel Drake, 2015): *"Set the reset_resume flag to trigger probe and upload the new firmware again."*
- `9e45524a01110` (Alex Lu, Realtek, 2019): global suspend without remote wakeup means the controller *"would drop the firmware"*.
- `8274db0776d12` (Max Chou, 2021) added `BTUSB_WAKEUP_AUTOSUSPEND` (sets `do_remote_wakeup` on autosuspend).
- On bluetooth-next the flag is set only for `!PMSG_IS_AUTO(message) && !device_may_wakeup()`
  (`btusb_main.c:4979-4982`), i.e. **system suspend only; a runtime suspend never sets it.**
- Oliver Neukum (2020), against a patch to avoid that reset: *"The device throws away its firmware when it does not need it."*
  (https://www.mail-archive.com/linux-kernel@vger.kernel.org/msg2323394.html; the patch,
  "Bluetooth: btusb: Avoid unnecessary reset upon system resume", is not in any local ref.)

**`btusb_needs_reset_resume_table` (Dell; Hans de Goede):**
- `fd865802c66bc` (Leif Liddy, 2017) DIY reset for QCA Rome → reverted by `7d06d5895c159`
  (Kai-Heng Feng): *"The USB device reset happens in btusb_open(), hence firmware loading gets interrupted."*
- `61f5acea8737d` (Hans, 2018-01): set `USB_QUIRK_RESET_RESUME` on the device instead, and says the
  core quirk *"also disables autosuspend for these devices, which is similarly broken"*.
- `1fdb926974695` (Hans, 2018-02): DMI match instead of USB ID, because *"The resume problems are actually a platform problem"*,
  and *"The USB_QUIRK_RESET_RESUME quirk also disables runtime suspend"*.
- `fc54910280eb3` (Hans, 2018-04): check the table only for QCA ROME.
- Hans's 2018-01 reply on "Disable autosuspend on QCA Rome devices": the quirk *"will also disable USB autosuspend since the btusb driver does not have a reset_resume callback"*
  (https://www.spinics.net/lists/linux-bluetooth/msg73701.html). That patch is not in any local ref.
- Alan Stern, 2023, on a Dell XPS 9360 QCA61x4: *"The USB core will not autosuspend a device that has the RESET_RESUME quirk"*;
  *"Apparently the RESET_RESUME quirk bit is set by the btusb driver itself"* (https://lkml.iu.edu/hypermail/linux/kernel/2311.2/05640.html).

**So btusb relies on the absence of `reset_resume` in two ways: (a) re-enumeration as the
recovery after a system reset-resume, (b) `autosuspend_check()`'s gate to keep the DMI-quirked
devices out of runtime suspend.** Patch D breaks both (as reviewers 6 and 7 found from the source).

Searches: `gitlog-s.sh bluetooth-next/master <s> -- drivers/bluetooth/btusb{,_main}.c` for
`btusb_needs_reset_resume_table`, `BTUSB_RESET_RESUME`, `reset_resume = 1`, `reset_resume`,
`BTUSB_WAKEUP_AUTOSUSPEND`; `git log --all --grep` for each unmerged subject; web search
"btusb reset_resume callback patch linux-bluetooth", "Oliver Neukum btusb reset_resume patch 2014".

## 2. The USB core side of BT-18

**The asymmetry is old, known to the USB maintainers, and was once nearly fixed.**

- `78d9a487ee961` (Alan Stern, 2008, as1024) introduced forced unbind/rebind for drivers lacking
  `reset_resume`, and only on the external (system) path: *"bind operations won't work during a system sleep transition"*, so it defers.
- `86c57edf60f5c` (Alan Stern, 2008, as1109b): *"if a normal resume fails … then a reset-resume is tried"* —
  the persist fallback that makes a *runtime* resume become a reset-resume (`hub.c:3694-3698`).
- Mainline `usb_resume()` (system): `unbind_marked_interfaces()` with the comment *"This can't be done in usb_resume_interface() above because it doesn't own the right set of locks"*;
  `usb_resume_complete()` rebinds. `usb_runtime_resume()` (`driver.c:2022-2032`) only calls
  `usb_resume_both()`. `usb_resume_interface()` skips the driver's resume while `needs_binding`
  is set (`driver.c:1362-1364`). Nothing else consumes `needs_binding` (`git grep`).
- **Upstream statement of exactly BT-18's mechanism:** `9be427efc7644` (Johan Hovold, 2016, Acked-by Alan Stern):
  *"unlike system resume, run-time resume does not honour it."* That revert fixed a system-resume
  regression; the runtime gap itself was left. Alan in that thread: *"would it help if usb_runtime_resume() did honor the needs_binding flag? I doubt it."*
  (https://lkml.iu.edu/hypermail/linux/kernel/1605.0/00585.html) — but about devices left
  runtime-suspended across *system* sleep (wakeup settings already lost), not about BT-18's case.

**Outside reviewer's claim, checked: "2014 Loic Poulain series to schedule a rebind work item after runtime resume; never landed." — VERIFIED.**
- "[PATCH] rebind: Add rebind mechanism for runtime-resume", "Poulain, Loic", 2014-03-10:
  https://go.mail-archive.com/linux-usb@vger.kernel.org/msg39089.html (adds per-interface `rebind_ws`,
  scheduled from `usb_runtime_resume()`; reason: the device lock *"may or may not already be held"*).
  - Alan Stern, same day: *"Although the basic idea is okay, this patch has a couple of weak spots."*
    (polling `usb_trylock_device()` loop; *"Can't you just call usb_lock_device_for_reset()"*; kerneldoc)
    https://www.mail-archive.com/linux-usb@vger.kernel.org/msg39100.html
  - Greg KH: only the Signed-off-by real name. https://www.mail-archive.com/linux-usb@vger.kernel.org/msg39099.html
- "[PATCHv3] …", 2014-03-12 (per-device work, calls `usb_unbind_and_rebind_marked_interfaces()`
  under the device lock): https://www.mail-archive.com/linux-usb@vger.kernel.org/msg39215.html — no reply in the archive.
- "[PATCHv4] …", 2014-04-02 (rebase): https://www.mail-archive.com/linux-usb@vger.kernel.org/msg40098.html.
  Alan Stern asked only how it differs from v3, changelog below `---` (msg40114); Loic: *"Same content, It's just a rebase"* (msg40126). No later message found.
- **Never landed:** no `rebind mechanism` subject in `git log --all`; no `rebind_ws`/`usb_queue_rebind` in mainline (`git grep`).
- What did land from it: `6aec044cc2f56` (Alan Stern, 2014-03-12, "USB: unbind all interfaces before rebinding any",
  *"Reported-and-tested-by: "Poulain, Loic""*, Cc stable) — the helper his v3/v4 call. A v2 was not found
  (searched mail-archive/spinics/marc/narkive for "PATCHv2 rebind runtime-resume Poulain").

**`autosuspend_check()`'s gate: the core's own answer, for the predictable case only.**
- Added by `f07600cf9eb3e` (Alan Stern, 2007-05, as918, "USB: add reset_resume method"): *"Don't allow autosuspend if the device will need a reset-resume and any of its interface drivers doesn't include support."*
- The `|| intf->needs_remote_wakeup` clause came with `9bbdf1e0afe77` (2010, "USB: convert to the runtime PM framework").
- It tests `udev->quirks & USB_QUIRK_RESET_RESUME` only (`driver.c:1963-1969`). A reset-resume
  chosen at run time by the persist fallback (`86c57edf60f5c`) is not foreseen by it; that is BT-18's path.

**Documentation:**
- `power-management.rst:330-336`: *"the driver won't receive any notification about the resume"*;
  *"Later kernels will call the driver's disconnect method"* — stale text from 2.6.23, never made true for runtime.
- `callbacks.rst:158-159`: *"suspend is always followed by one of: resume, reset_resume, or disconnect."* — BT-18 violates it.
- `persist.rst`: the persist reset also happens *"if a USB device fails to carry out a normal resume"*; says nothing about runtime vs. system or drivers lacking `reset_resume`.
- **No document says drivers without `reset_resume` must avoid runtime PM.** Searched
  `git grep -i "reset.resume|rebind|needs_binding|reprobe|re-?enumerat"` in those three files.

**Recent maintainer stance on adding `reset_resume` to a driver to dodge rebinding** (usblp,
"[PATH v2] usb: usblp: add the reset_resume function interface", 2026-03,
https://ratatoskr.run/linux-usb/2026/03/8893269/t): Alan Stern: *"hiding the bug by setting the reset_resume callback will not fix it."*;
Oliver Neukum NACK: *"Implementing reset_resume() for usblp is basically impossible."* Same argument as for btusb.

## 3. Prior reports similar to BT-17

- **2011, autosuspend default revert:** `78794b2cdeac3` (Linus) reverts `556ea928f78a3` (btusb autosuspend
  by default): devices *"just stop responding after a while"* with *"no reset_resume for driver btusb?"*;
  bugzilla 26182 "btusb hangs after resetting USB device" (page bot-blocked; title from search).
  Linus: *"I have no idea whether this is a USB-level issue, or a driver-level one."*
  (https://lkml.rescloud.iu.edu/hypermail/linux/kernel/1102.2/03661.html). The closest historical BT-18 match; its mechanism was never pinned down.
- **2018, QCA ROME after runtime resume:** Launchpad 1741206 (Kai-Heng Feng), *"does not work after runtime suspend/resume"* with the then reset-resume quirk; led to `7d06d5895c159`. https://bugs.launchpad.net/bugs/1741206
- **QCA Rome / Atheros after system resume, tx timeouts:** bugzilla 193571 (power-cycle needed), Red Hat 1514836 (the Dell DMI table). Workaround everywhere: `btusb.enable_autosuspend=n` (bugzilla 199351, Red Hat 1589548).
- **`btusb.enable_autosuspend` history:** `556ea928f78a3` (2010) → reverted `78794b2cdeac3` (2011); Kconfig
  `BT_HCIBTUSB_AUTOSUSPEND` + module option `eff2d68ca7388` (Hans, 2017: *"not entirely without risk of regressions"*);
  `7bd9fb058d772` (2021) reverted by `895915226a598`.
- **13d3:3503 itself:** added to the quirks table by `dc16388d45ecb` (Tibor Harcsa, 2026-06-29; QCA ROME, wideband speech). It says nothing about PM.
- **`dcaf83ead130` thread** (Rong Zhang, v1 2026-06-29, v2 2026-07; merged via `for-net-2026-09-08`;
  `Fixes: e31d761628ad`, which had disabled wakeup outright):
  - MediaTek (Chris Lu) on the first patch: issue *"strongly related to the platform's USB hub"* behaviour and *"looks like a workaround"*, wanting *"a better way"* (https://lkml.iu.edu/2606.3/04802.html).
  - Luiz von Dentz (v1 review) questioned whether the detection could match built-in controllers or external ports on Zen; he did not ask for a generic fix (https://lkml.iu.edu/2606.3/12419.html).
  - **Nobody asked for, or rejected, a generic btusb or USB-core fix.** Root cause left open: *"Resetting the xHCI root hub doesn't help at all"*; MediaTek was still *"looking for an AMD platform that can reproduce"* (https://lkml.iu.edu/2607.3/01067.html).
- **Searched, nothing matching BT-17 (idle QCA9377 dead at a runtime resume, `0x0c24`):** web "QCA9377 bluetooth 13d3:3503 autosuspend tx timeout btusb";
  "\"Failed usb_autopm_get_interface\" btusb bluetooth" (no hit for the string); "bluetooth stops working after idle autosuspend btusb command 0x0c24 tx timeout launchpad OR github"
  (only generic forum threads, e.g. Manjaro, with `power/autosuspend` workarounds); bugzilla.kernel.org directly is bot-blocked, so only search-engine hits were seen.

## 5. Rules and preferences

**linux-usb / USB core:**
- `MAINTAINERS` "USB SUBSYSTEM": `M: Greg Kroah-Hartman`, `L: linux-usb@vger.kernel.org`, `F: drivers/usb/`, `include/linux/usb.h`. **No `P:` line** in any USB or Bluetooth section (awk over `MAINTAINERS`); `maintainer-handbooks.rst` lists no USB profile.
- Alan Stern is `M:` only for EHCI/OHCI/UHCI/mass storage, yet Acks or Reviews most core PM commits (`--full-history` log of `driver.c`/`hub.c` since 2020, e.g. `2521106fc732b`, `8f5b7e2bec1c3`, `9671d55037065`, `1ade6a4f7f09d`). He wrote `driver.c`'s PM code (`f07600cf9eb3e`, `78d9a487ee961`, `9bbdf1e0afe77`, `6aec044cc2f56`). `get_maintainer.pl --git` would likely add him; Cc him by name.
- RFCs: Greg (2015) *"I personally ignore RFC patches unless they are tiny"* (https://lkml.iu.edu/hypermail/linux/kernel/1507.0/00442.html). Alan and Oliver do answer questions and RFCs in substance (2026-08 "usb: core: defer leaf-device resume" RFC: Alan *"Overall this does not sound like a good idea."*, with alternatives; https://ratatoskr.run/lkml/2026/08/17369900/t). So: a plain question or a real patch, not an "RFC PATCH" addressed to Greg.
- How core PM changes are argued/tested: bug-driven, a concrete failing scenario with log, `Tested-by` from reporters, `Closes:` to a lore report (`9bd9c8026341f`, `a49e1e2e785fb`, `f59f93cd1d720`). Emulation is acceptable when described: `0e8baa78d872f` (2026-09, Acked-by Alan Stern): *"Tested in QEMU … using dummy_hcd and raw-gadget"*; `9c6d778800b92` (Alan Stern) with a QEMU trace.

**Bluetooth / btusb:**
- `BLUETOOTH DRIVERS`: Marcel Holtmann, Luiz Augusto von Dentz, `linux-bluetooth`; no `P:`.
- btusb since 2023 (`bluetooth-next`, 241 commits): committer Luiz in 235. Reviewed-by/Acked-by on 27: Paul Menzel 19, others ≤2; Alan Stern once (a core API change, `49a78b05d5ca1`). **btusb PM changes are reviewed by Luiz alone in practice**, plus whoever is Cc'd.
- Tests: 15 of 241 carry `Tested-by`; 33 mention "tested", mostly new IDs (`--grep` counts). The CI bot maps no tester to a btusb-only change (our README). **btusb changes usually come with no test beyond the author's statement.**

**Cross-subsystem question:**
- Precedent of one thread with both camps: 2011 "btusb autosuspend (was Re: Linux 2.6.38-rc6)", where Linus pulled in Bluetooth and USB people and Oliver Neukum answered (https://lkml.iu.edu/hypermail/linux/kernel/1103.0/00111.html). The 2023 QCA61x4 power thread had Alan Stern, Greg and a Qualcomm developer in one thread. The 2014 Neukum and Poulain mails went to linux-usb.
- `5.Posting.rst`: copy *"Other developers who have been working in the same area - especially those who might be working there now."*
- **Recommendation from precedent:** one thread, To linux-usb + Alan Stern + Greg, Cc linux-bluetooth + Marcel + Luiz (+ Oliver Neukum, author of btusb's PM code `7bee549e197c`, and Johan Hovold, author of `9be427efc7644`). The question is core-side; Bluetooth is the user.

## What this changes

- **A (BT-20):** unaffected by prior art; nobody else touches `btusb_waker`. Rhodes's unmerged rewrite touches the neighbourhood: rebase-check against it if it moves. Oliver's 2017 rule (*"abort the operation and report an error"*) supports logging the failure.
- **B (BT-19):** rebase on `c93922dd316b7` (already in bluetooth-next): B's early return must sit before `usb_autopm_get_interface()` and leave the `BTUSB_RESET` accounting balanced. Cc Jiajia Liu. The `c93922dd` v4 note ("in case the first reset failed") backs reviewer 7's finding that a queued reset can be lost.
- **D (BT-18, btusb side):** prior art is against it. Hans 2013 (re-enumerate), Marcel 2015 (replay is *"a lost cause"*), Oliver 2014/2017, and Alan/Oliver on usblp 2026 all reject a btusb `reset_resume` that calls `btusb_resume()`. D also defeats the gate Hans relied on (`61f5acea`, `1fdb9269`). Keep D local as the fallback only.
- **E (BT-23):** confirmed unfixed upstream since 2009, and not fixed by Rhodes's pending rewrite (it keeps the anchor outside `txlock`). If his series moves, say so below `---`. `Fixes: 7bee549e197c` stands.
- **BT-24:** untouched since `7bee549e197c`; nobody is on it.
- **C (RFC):** `dcaf83ead130` precedent holds; MediaTek's "platform USB hub" view and the absent root cause mean an RFC needs the A/B evidence first. Greg ignores RFCs; this one is for linux-bluetooth only.
- **The BT-18 question to linux-usb:**
  - Frame it as the known gap: cite `9be427efc7644` (*"run-time resume does not honour it"*) and the 2014 Poulain series (Alan: *"the basic idea is okay"*), which stalled after v4 with no technical objection on record.
  - Ask whether a deferred rebind from `usb_runtime_resume()` (Poulain v3's shape: per-device work, `usb_lock_device_for_reset()`-style locking per Alan's v1 review) is still wanted, or whether `autosuspend_check()` should also refuse autosuspend when persist could force a reset-resume and a driver lacks `reset_resume`.
  - Point at `callbacks.rst`'s *"resume, reset_resume, or disconnect"* and the stale `power-management.rst:334-336`.
  - Mention Alan's 2016 doubt and why it does not apply (system sleep, wakeup settings lost).
  - Send as a question or a real patch, not an "RFC" to Greg; one thread, linux-usb To, linux-bluetooth Cc, Alan Stern, Oliver Neukum and Johan Hovold by name. Describe the emulation in the body; a link only by decision.
