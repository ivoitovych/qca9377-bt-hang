# CO-46: journalctl slows in proportion to the number of journal files

**Target:** systemd (`sd-journal`, used by `journalctl` and libsystemd0).

- upstream's fix identified and measured on the laptop and in containers;

- packaging done: two quilt patches, a debdiff against 8.19, the packaging-branch commit, an amd64
  test build installed and tested in a fresh container.

`sru-noble/` is **under review, not ready to send** (its checksums are in `sru-noble/SHA256SUMS`).
Its `From: <AUTHOR-NAME> <AUTHOR-EMAIL>` lines are placeholders on purpose, for the submitter's

## The incident that found it (2026-11-14)
`devtools/check`'s journal-contract step ran `journalctl -k -b all` and counted every boot
separator, though it needed only the first. With BT-17's dynamic debug on, it ran 7 h 44 min at
a full CPU. It read 5.4 GB from the journal files and wrote 1.29 GB of text, about 46 KB/s.
- Our part was fixed in `69d24d1`: `grep -m1`, 3.4 s, the same verdict.
- Record: `docs/STATUS.md`, "Repository health".

## Cause (v255.4)
- `real_journal_next()` compares the next entry of every open file on every step.
- `next_beyond_location()` begins with `journal_file_read_tail_timestamp()`, which begins with an
  `fstat()`; `compare_boot_ids()` reads two more tails.
- With 100 files open the installed journalctl makes 477.8 `fstat`-family calls per printed line (corrected 2026-11-16 from 477.7, the value
in `sru-noble/evidence.md`).

|---|---|---|---|
| 25 | 29 194 | 201 342 | 7x |
| 100 | 11 361 | 133 097 | 12x |
| 479 | 2 292 | 56 894 | 25x |

- **Everyday queries:** `journalctl -b` is 35 times faster, 48 s against about 28 min.
- **Containers:** they make every system call dearer, so the gain there looks larger (15–77 times).
  The host's figures are the ones to quote.
- **Growth with the number of files:**
  - with A and B, the exponent is still 2.15 on synthetic data (1.50 on the real journal);
  - our priority-queue prototype on main is flat: exponent 1.13, about 205 000 to 305 000 lines/s
    at every file count;
  - the prototype is not for sending.
- **The reproducer:** `sru-noble/reproducer/`, no root, temporary directory only. Tested as an
  unprivileged user in a fresh ubuntu:24.04 container, with a before-and-after check of the system's
  log and config directories.

2. **Review** by the operator's reviewers (`sru-noble-review-request.md`), then the operator files.
3. **Upstream, the remaining growth: measured 2026-11-16**
   (branch `research/journalctl-file-scaling`, path `results/journalctl-file-scaling-remaining-2026-11-16/`,
   [link](https://github.com/ivoitovych/qca9377-bt-hang/tree/research/journalctl-file-scaling/results/journalctl-file-scaling-remaining-2026-11-16);
   host, main at the PR's base `32d75628c4`):
   - **PR #44579** (head `f26f6637ac`, a cached winner and runner-up) removes the growth for
     sequential (rotated) files. Exponent 1.05; 397 000 lines/s at 800 files against main's 7 000.
     It does not help interleaved files: at 400 files it gives 132 000 lines/s, main 131 000.
   - **Our priority-queue prototype g** is flat in all layouts:
     - interleaved at 400 files: 377 000 lines/s with one machine, 498 000 with three (2.8 and 7
       times the PR);
     - sequential: 1.1 to 1.7 times slower than the PR (235 000 at 800 files).
   - **Correctness:** both are byte-identical to main in 336 comparisons. That covers 2 and 3
     machines, overlapping boots, matches, cursors, reverse, `-f` on a live file, and files added or
     removed mid-read. The journal unit tests pass 44 of 44.
   - **The only differences** are on journals that break journald's invariants: monotonic time
     restarting within a boot, or repeated sequence numbers. There, main's own order depends on scan
     order, so no build is "right".
   - **Before g could be proposed:**
     - a test of its own;
     - style fixes: two long lines and a test-only `#ifndef`;
     - clang-tidy;
     - a rebase over the PR, since both change `real_journal_next()`.
   - **Upstream's rules:** systemd's CONTRIBUTING requires that the author understands the code and
     that no agent opens PRs or posts. Its agent-guidance file requires a marker in `README.md` on
     any source change. The PR's review so far is one maintainer comment that asks the author to
     address the automated review's points first.
   - How to engage (data on #44579, a separate PR, or nothing) is the operator's decision.
4. **On the laptop** (operator's decision): installing a patched systemd; or fewer, larger files.
   Our scripts use `--list-boots`, `-b` and `grep -m1`, so they do not read the whole journal.
