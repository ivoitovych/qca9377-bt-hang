3. Incoming-SCO test (reviewer 2): the remote device sets up the link, no local socket holds it, a local socket connects
  Source facts: a link the remote device set up is created in the event handlers; its hci_conn keeps setting = 0 and codec = 0
  (hci_conn_add never sets them). When the last holder drops a SCO connection, hci_conn_drop() queues the idle disconnect with
  delay 0 (hci_core.h:1792, "default: timeo = 0"): the window "link up, no holder, worker not yet run" is microseconds, so
  the emulator cannot hold it without help. The held-link case is deterministic.
  Tests (tools/sco-tester.c on branch l7-incoming of lane7's bluez; proposal/*.patch; research, not for posting):
    "Connect Over Incoming Link" and "Connect Transparent Over Incoming Link": the accepted socket of a listening socket stays
        open (a holder); a second socket connects (default CVSD / transparent): expect -EBUSY, link stays, no setup sent.
    "Connect Over Closed Incoming Link" and "Connect Transparent ...": the accepted socket is closed and a connect() follows
        while the idle-disconnect worker is held back by the debug-only parameter w2c_park_ms (kernels ebase/e12/e123 hold it
        before it reads the holders; parkbase/parkB/parkC after it saw none). Expect -ECONNABORTED, then, once the remote link
        is gone, a retry gets a link of its own (one setup command, a second Synchronous Connection Complete).
        A kernel without the parameter reports Not Run.
  Results (3 runs each; logs run-early-*, run-late-*, run-full-*):
                          holder cases (2)   no holder, worker held back BEFORE its holder check | AFTER it
    base                  EBUSY, pass        connect() returns 0, adopts the link: FAIL          | FAIL
    patches 1+2           EBUSY, pass        connect() returns 0, adopts the link: FAIL          | -ECONNABORTED, pass
    patches 1+2+3         EBUSY, pass        -ECONNABORTED, retry gets a link: pass (30 of 30 runs that ran to the end, see 7) | pass
  What it shows. For a link the remote device set up, patch 2 alone refuses only when the worker had already set abort_reason;
  a connect() that comes before that is reported connected on the remote device's link, with the default CVSD setting and
  with a transparent one: a transparent socket silently gets a CVSD link, which is what patch 3 prevents. Patch 3 refuses both,
  once. It also refuses a connect() whose parameters match the link, because the stored parameters of such a link are zero:
  compatible and other cannot be told apart (that is the F-22 left out in the package's NOTES; it needs CO-21's stored air
  mode). The retry works. With a holder the answer is -EBUSY on every kernel, as before.
  The patch 3 message and the single-patch note now say this. The holder cases pass on base too: regression guards, not
  evidence for patch 3. The closed cases need a debug kernel, so they cannot be posted as BlueZ tests.

5. cancel_delayed_work_sync(&sco->disc_work) under hdev->lock (reviewer 2): cancel-sync-analysis.txt
  Reviewer 7's argument holds for hdev->lock: for SCO/eSCO hci_cancel_connect_sync() returns -ENOENT without a lock,
  hci_proto_disconn_ind() returns a constant, the abort is queued on cmd_sync_work and not run in the worker. It is not
  complete: the worker takes hdev->cmd_sync_work_lock (lookup) and hdev->unregister_lock (submit) briefly, and
  add_device_complete() / add_ext_adv_params_complete() take hdev->lock under cmd_sync_work_lock in hci_cmd_sync_clear() (only
  at unregister). That is a three-way cycle that needs a running SCO disc_work, a connect() onto it, and an unregister with an
  Add Device queued. It is not new: hci_conn_del() waits for the same work with hdev->lock held (hci_dev_close_sync() ->
  hci_conn_hash_flush()), so the patch adds no lock ordering that is not already there; patch 2's message now says that
  after "does not take that lock". Lockdep guests (all of section 2, and the parked-worker kernels where the wait really
  blocks): no report. Not shown by a run: the cycle itself (it needs three paths in one boot; no injection was built).
