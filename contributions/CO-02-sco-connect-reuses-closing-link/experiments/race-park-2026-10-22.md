# CO-02 — the parked-worker race runs, 2026-10-22

This is the deterministic evidence for patch 3. A debug-only kernel change parks
`hci_conn_timeout()` right after it has seen `refcnt == 0` for a SCO connection. While it is
parked, a scratch tester case closes the first socket and connects a second one. Neither change
is part of any submission. Results summary: `results-2026-10-22.md` (the linked case, v1) and
`results-2026-10-22-v2.md` (the incoming case; v2).

## The park (scratch commit `f672e0b632559`, applied on top of the series)
```diff
+static unsigned int w2c_park_ms;
+module_param(w2c_park_ms, uint, 0644);
+
 static void hci_conn_timeout(struct work_struct *work)
 {
@@
 	if (refcnt > 0)
 		return;
 
+	if (w2c_park_ms && (conn->type == SCO_LINK || conn->type == ESCO_LINK)) {
+		pr_warn("w2c: hcon %p saw refcnt 0, parking %u ms\n", conn,
+			w2c_park_ms);
+		msleep(w2c_park_ms);
+		pr_warn("w2c: hcon %p released: refcnt %d abort_reason %u\n",
+			conn, atomic_read(&conn->refcnt), conn->abort_reason);
+	}
+
 	hci_abort_conn(conn, hci_proto_disconn_ind(conn));
```

## The scratch cases (`cache/co02-w2c-bluez-exp`, branch `co02/w2c-race-experiment`)
- **"EXPERIMENT eSCO CVSD - Race Park":** the host connects a first socket and writes 1500 to
  `/sys/module/bluetooth/parameters/w2c_park_ms`. It closes the socket, and 300 ms later, while
  the worker is parked, it connects a second socket to the same device. After 2.7 s it checks
  `SO_ERROR` and `poll()` on the second socket.
- **"EXPERIMENT eSCO CVSD - Incoming Race Park":** the same, except the first link is set up by
  the remote device (`bthost_setup_sco`), and the host accepts it and then closes the accepted
  socket. Such a connection never gets an `hci_link`.

## One run of each (the `w2c:` lines are the kernel's; the rest is the tester's)
**v1 series + park (`81a4f099a665`), incoming:** failed, 2 of 2 alike
```
RACE incoming link accepted
RACE first socket connected, closing it (worker parks)
w2c: hcon ffff888001f10000 saw refcnt 0, parking 1500 ms
RACE second connect() returned 0 (Success), poll 0x0004
RACE mid: poll 0x0004, SO_ERROR 0, Disconnect 0
w2c: hcon ffff888001f10000 released: refcnt 1 abort_reason 0
RACE end: poll 0x001c, SO_ERROR 103 (Software caused connection abort), setup 0, Disconnect 0, Sync Complete 0
RACE CONFIRMED: second socket was connected and then killed by the parked abort
```
The worker had seen no holder and aborted the connection anyway after the new connect took its
hold (`refcnt 1`). No setup was sent for the second socket.

**v2 series + park (`c4c1c670e607`), incoming:** passed, 6 of 6 alike
```
RACE incoming link accepted
RACE first socket connected, closing it (worker parks)
w2c: hcon ffff888001be8000 saw refcnt 0, parking 1500 ms
w2c: hcon ffff888001be8000 released: refcnt 1 abort_reason 0
w2c: hcon ffff888001be8000 saw refcnt 0, parking 1500 ms
RACE second connect() returned -1 (Software caused connection abort), poll 0x0004
w2c: hcon ffff888001be8000 released: refcnt 0 abort_reason 19
RACE end: poll 0x0004, SO_ERROR 0 (Success), setup 0, Disconnect 0, Sync Complete 0
```
The connect waits in `cancel_delayed_work_sync()` until the parked worker finishes. It then sees
`abort_reason` set and refuses, and its dropped hold queues the work once more. That second park
finds `abort_reason` already set, so `hci_abort_conn()` returns at once.

**v2 series + park, linked ("Race Park"):** passed, 3 of 3. The second `connect()` returned -1
(Software caused connection abort).

All parked logs are clean in `kernel-report-scan`. The kernels have lockdep and
`DEBUG_ATOMIC_SLEEP` on, and the wait really blocks for the park's 1.5 s under `hdev->lock`.
Raw logs on the development host: `tmp/co02-round2/runs/race-*.log`.
