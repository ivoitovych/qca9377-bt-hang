## The reproducer (`patch/bluez/`)
Two `sco-tester` cases:
- **"eSCO CVSD - Reconnect During Disconnect":** a hook on the Disconnect command lets the
  emulator answer Command Status but holds the Disconnection Complete; 100 ms later a second
  socket connects to the same peer; 300 ms later the held event is delivered (reason 0x16).
  It passes if the connect is refused, or if the second socket gets its own setup and stays up;
  it fails if the socket reports connected and then errors.
- **"eSCO CVSD - Reconnect After Disconnect"** (control): the same with the event delivered
  before the second connect.
Every command the controller receives is logged. checkpatch 0/0, gitlint pass.

## The candidate fixes
1. `patch/kernel/0001` **refuse to reuse a SCO connection that is being aborted:** in
   `hci_connect_sco()`, a connection with `abort_reason` set fails the connect with
   `-ECONNABORTED` (dropping the ACL hold just taken). `Fixes: a13f316e90fd` (v6.6, which
   stopped setting `BT_DISCONN` in `hci_abort_conn()`; the tag is our inference from that
   commit's diff).
2. `patch/kernel/0002` **take the caller's hold when a SCO connection is reused:** a second
   defect found on the way. A second `connect()` to a peer with a SCO link up returns EBUSY,
   and then the first socket's link is disconnected (base: 3/3; the log shows EBUSY, a
   Disconnect, the first socket's `SO_ERROR 103`). Since `06149746e720` (v6.4) the only hold
   comes from `hci_conn_link()`, which takes none for an existing link, while `sco_connect()`
   still drops one. `Fixes: 06149746e720`. The cause is read from the code (it mirrors the CIS
   fix `e06d549fcd4a`); the symptom is measured.
3. `patch/kernel-rfc-defer/` **deferral prototype (RFC):** the socket goes to `BT_CONNECT` and
   the connect is queued behind the abort; `connect()` returns EINPROGRESS and a fresh setup
   follows the Disconnection Complete.

All three: `checkpatch --strict` clean, W=1 `-Werror` clean, sparse `C=2` no new findings.

## Does it fix U7 end to end?
PipeWire 1.0.5 retries an immediate `ECONNABORTED` twice, within microseconds
(`backend-native.c`, its retry loop from commit `d439b7cdd`, 2021). Emulated with a new socket
and two immediate retries:

| kernel | PipeWire-style retry |
|---|---|
| unpatched | fail 3/3 |
| refuse | fail 3/3 |
| refuse + hold | fail 3/3 |
| deferral | pass 3/3 (UP), 3/3 (SMP) |

So **refusing alone does not rescue PipeWire 1.0.5**: its retries come before the old link is
gone (tens to hundreds of ms). Refusing turns a silent dead socket into an error at acquire
[inference: what WirePlumber then does is not checked]. Deferral fixes it in the emulator.
