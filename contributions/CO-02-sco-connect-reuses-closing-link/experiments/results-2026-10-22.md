## The residual race (reviewers 2, 3, 5): real, closed by patch 3
`hci_conn_timeout()` reads `refcnt` without a lock and calls `hci_abort_conn()` with no
re-check (`hci_conn.c:641-662`, `:3270-3300`). A scratch, debug-only module parameter parks it
right after it saw `refcnt == 0`; a tester case closes the first socket and connects a second
during the park.

| kernel | second connect | parked worker on release | result |
|---|---|---|---|
| unpatched base | "returned 0 (Success)" | `refcnt 0` (no hold taken: patch 2's bug) | killed, `SO_ERROR 103` (2/2) |
| patches 1 and 2 | "returned 0 (Success)" | `refcnt 1 abort_reason 0`, aborts anyway | killed, `SO_ERROR 103` (4/4 W2c, 2/2 re-check) |
| + patch 3 | waits, then "Software caused connection abort" | aborts as decided | refused cleanly, Passed (3/3 W2c, 2/2 re-check) |

**Why patch 3 cannot deadlock:** for SCO, `hci_proto_disconn_ind()` returns a constant
(`hci_core.h:2191-2192`) and `hci_abort_conn()` only sets `abort_reason` and queues the sync work,
taking no `hdev->lock`; and `hci_conn_del()` already waits for `disc_work` with `hdev->lock` held
(`hci_conn.c:1300`), so the lock order exists in mainline already. Not done: the check widened
to `refcnt == 0`, which reviewer 6 warned against (incoming SCO sits at 0 in `BT_CONNECT`).
