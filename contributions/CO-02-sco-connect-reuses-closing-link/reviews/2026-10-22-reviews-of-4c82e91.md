### What the contribution is
CO-02 is a two-patch kernel series for `bluetooth-next` plus a separate BlueZ `sco-tester` case:

A control case and broader tester suites are included. ### 1. The BlueZ test currently has a real false-pass hole

This is the clearest issue I found.

The shared `reconnect_check()` treats an immediate `connect()` failure as success whenever the errno is anything other than `EAGAIN`/`EINPROGRESS`. Consequently:

- **Reconnect During Disconnect** can pass for an unrelated failure such as `ENOMEM`, `EINVAL`, `EHOSTUNREACH`, etc.
- More importantly, **Reconnect After Disconnect**, which is supposed to prove that a fresh connection actually works after the old one has gone, can pass simply because the new connect was rejected immediately.

That undermines the value of the negative control. The test can certify a broken implementation.

For a regression test submitted upstream, I would make the oracle much stronger. “After Disconnect” should require an actual successful connection/link. “During Disconnect” should explicitly accept only the behavior you intend to permit—currently `ECONNABORTED`, or a real new successful connection if you deliberately want the test to remain compatible with a later defer implementation. It should not mean “any error is fine.”

This is a **must-fix before submitting the BlueZ patch**.

Apart from that, the test machinery is not obviously overengineered. I checked the use of the emulator hooks; BlueZ already has comparable `HCIEMU_HOOK_PRE_EVT` machinery in its testers. The fixed timing is backed by your repeated SMP/KCSAN runs. The patch is large for two test cases, but the emulator setup explains most of that. Once the oracle is strict, I think the size is defensible.

### 2. There is a narrow `disc_work`/new-hold race that Patch 1 has not yet demonstrated it closes

This is the part I would investigate before mailing the kernel series.

Current ownership behavior is approximately:

```text
hci_conn_drop(SCO)
  refcnt -> 0
  queue disc_work with delay 0

hci_conn_timeout()
  refcnt = atomic_read(...)
  if refcnt > 0
      return
  hci_abort_conn(...)
      abort_reason = ...
```

Whereas `hci_conn_hold()` does:

```text
atomic_inc(refcnt);
cancel_delayed_work(&conn->disc_work);
```

and that cancellation is **not synchronous**.

There is therefore a plausible interleaving:

```text
timeout worker                   new connect

reads refcnt == 0

                                 finds existing SCO
                                 sees abort_reason == 0
                                 hci_conn_hold(sco)
                                   refcnt -> 1
                                   cancel_delayed_work()
                                   [too late: worker is running]
                                 returns connection

sets abort_reason
starts abort
```

In that ordering, Patch 1's `abort_reason` check has already happened before the timeout publishes the abort, and Patch 2's new hold does not necessarily stop the running timeout.

Your current 100-ms test is excellent for the **abort-already-established** case. It deliberately lets the abort get under way and demonstrates that `abort_reason` catches it. It does **not** exercise this handoff boundary where `disc_work` has started but has not yet called `hci_abort_conn()`.

I am not claiming that I have demonstrated this race on a running kernel. I am saying the source permits an interleaving that I cannot prove safe from the existing evidence. Since your own review request specifically asks reviewers about the race with `hci_conn_timeout()`, I would not leave that question for Luiz or Marcel to discover.

The cleanest next experiment is deterministic rather than probabilistic: put a temporary test barrier in `hci_conn_timeout()` immediately after it observes `refcnt == 0`, start the second SCO `connect()`, let it reach/reuse/hold the existing `hci_conn`, then release the timeout worker. If the new socket subsequently receives the old abort, you have a concrete reproducer for the remaining race. If another mechanism prevents that interleaving from becoming harmful, you have strong evidence to document.

This matters especially because timeout/refcount behavior around `hci_connect_sco()` is an actively troublesome area: syzbot still has an open `WARNING in hci_connect_sco` report, although I would **not** assume that report has the same cause. [Syzkaller](https://syzkaller.appspot.com/bug?extid=5897b3c764f5989ea942)

### Patch 2 is particularly convincing

The revised `Fixes: 8a5b0135d4a5` is, in my view, the right choice.

`06149746e720` introduced the asymmetry: `hci_conn_link()` takes a hold when creating a link but returns an existing link without another hold. That alone does not yet create the observed destructive behavior. Cen Zhang's `8a5b0135d4a5` later made `sco_connect()` drop the returned `hci_conn` when `sco_chan_add()` fails. The two changes together mean an EBUSY second connect can drop ownership belonging to the first socket.

That is exactly the sort of causal `Fixes:` selection maintainers want: identify the commit that made the bug observable, not merely the oldest piece of code participating in it.

Even more importantly, there is now a **near-perfect accepted precedent**. The September fix `Bluetooth: hci_conn: fix CIS hold ownership on reuse` corrects essentially the same contract problem: an existing `hci_conn_link()` returns without acquiring the hold that its caller assumes it owns. Its solution explicitly preserves a hold for the caller in the reuse path. [Openwall Lists](https://lists.openwall.net/linux-kernel/2026/09/15/2710)

That patch was accepted and subsequently assigned CVE-2026-98462 and backported through several stable lines. [Openwall Lists](https://lists.openwall.net/linux-cve-announce/2026/10/18/20)

So Patch 2 is not inventing an exotic ownership convention. It follows a pattern that Bluetooth maintainers have **just accepted in this exact subsystem**. That is powerful evidence in its favor.

## 2. Technical review of the kernel patches

### Patch 1 — Refuse reuse of an aborting SCO connection

`Bluetooth: hci_conn: don't reuse an aborting SCO connection`

I examined the final diff and compared its intended behavior with the SCO connection and teardown paths.

The mechanism is convincing:

- A SCO connection remains in `BT_CONNECTED` while disconnection is pending.
- The existing lookup can return that connection to another caller.
- No new synchronous connection setup is initiated.
- The new socket can consequently report success despite having no usable new link.
- The later Disconnection Complete closes that socket.

The proposed `abort_reason` check addresses exactly this condition. Dropping the newly acquired ACL hold before returning `-ECONNABORTED` also makes sense.

This is an appropriate, localized fix. It is much easier to review than redesigning SCO connection scheduling.

My concern is the race at the boundary between scheduling disconnection and setting `abort_reason`.

In the upstream implementation examined, `hci_conn_hold()` increments the connection's hold counter and calls `cancel_delayed_work()`. Meanwhile, `hci_conn_timeout()` can execute asynchronously, observe no remaining holds, and call `hci_abort_conn()`.

A possible interleaving is:

Disconnect worker

CPU A

Reads hold count = 0

Worker continues toward `hci_abort_conn()`

Sets `abort_reason`

Second connect

CPU B

Finds existing SCO connection

Reads `abort_reason == 0`

Takes an additional hold

Question: Can the disconnect worker proceed after the new hold was taken, resulting in a connection returned to the second caller that is nevertheless being aborted?

The existence of that harmful interleaving has not been established by this review. It requires confirmation against the exact `27731ba09195` tree, including locking and workqueue synchronization.

Nevertheless, this is precisely the type of concurrency question that can generate substantial maintainer discussion after submission.

Priority: High. I recommend a forced interleaving test, or a documented source-level explanation proving this race harmless, before sending.

### Patch 2 — Hold a reused SCO connection for its caller

`Bluetooth: hci_conn: hold a reused SCO connection for its caller`

This patch also addresses a real, well-motivated defect.

The important ownership distinction is that `hci_conn_link()` establishes its connection hold when a new link is created, but returning an existing link does not acquire another hold.

A second `connect()` can therefore obtain a pointer to a live SCO connection without acquiring the hold that its caller's error path expects to release.

The resulting incorrect decrement explains the observed `EBUSY` followed by disconnection of the first socket's link.

Your correction is consistent with the ownership model: take a caller-specific SCO hold when reusing an existing link, and release the redundant ACL hold already covered by the established parent-child relationship.

I found no clear accounting error in the final diff.

There are nevertheless two points worth documenting.

First, `hci_connect_sco()` still updates `sco->setting` and `sco->codec` even when the second socket will subsequently fail attachment with `EBUSY`. That behavior predates your patch, but it means a failed duplicate connect can change parameters stored on the existing connection. Establish whether those assignments have consequences for subsequent operations. If so, that should probably become a separate follow-up rather than expanding CO-02.

Second, the upstream test package does not currently include the dedicated second-connect test used to establish this defect. The investigation contains convincing private measurements, but the mailed cover letter does not expose them clearly enough.

Priority: Medium. The ownership fix looks sound, but its regression evidence should be easier for maintainers to evaluate.

## 3. Review of the BlueZ regression test

This is where I found the most actionable improvements.

The [BlueZ patch](https://github.com/ivoitovych/qca9377-bt-hang/blob/4c82e91900f0599e6a6c4310d5eefa996c78f344/contributions/CO-02-sco-connect-reuses-closing-link/patch/bluez/0001-tools-sco-tester-Add-reconnect-tests.patch) adds 346 lines and changes one existing line.

A substantial test for a small kernel correction is not inherently wrong. Controlling controller event ordering can require more code than the fix itself. But every new test line creates maintenance obligations for BlueZ.

### Finding A — The test accepts unrelated failures as success

High priority

In `reconnect_check()`, the test accepts any immediately refused second connection other than `EAGAIN` and `EINPROGRESS`.

That means an unexpected failure such as `EINVAL`, `EOPNOTSUPP`, or another unrelated error could make the regression test pass.

The desired kernel behavior is more specific.

For the refusal implementation, `ECONNABORTED` is expected. For a deferral implementation, success must be supported by evidence that a new link was actually established.

I recommend distinguishing those two acceptable outcomes explicitly rather than treating all refusal errors as equivalent.

The same problem affects the After Disconnect control test, which should require successful establishment of a fresh link—not arbitrary refusal.

### Finding B — The synthetic disconnect does not reproduce complete controller teardown

High priority

I checked the emulator implementation at BlueZ revision `7bc9684dc9e4`.

The test intercepts the Disconnect command through `HCIEMU_HOOK_PRE_EVT` and returns `false`. This is a valid hook point: the emulator's command processing has already produced Command Status.

However, it also prevents the normal `cmd_disconnect_complete()` path from executing.

That normal path removes the controller-side connection record and performs the corresponding cleanup. The new test later manually injects a Disconnection Complete event using `btdev_send_event()`.

Consequently, the guest kernel can believe the SCO link has disappeared while the emulator retains internal state for that connection.

This does not invalidate the reproduced false-success defect. It does limit the test's fidelity, particularly for verifying that a deferred reconnect successfully establishes an entirely new controller-side connection.

A cleaner approach would be to intercept and delay the outgoing Disconnection Complete event while allowing the emulator's normal connection removal to proceed.

The delayed event can then be released after the desired interval.

That would provide a more faithful representation of controller state and reduce the risk of accepting behavior that could not occur on real hardware.

### Finding C — Missing assertions on the controlled scenario

The test tracks `disc_held`, setup command counts, synchronous completion counts, and connection handles.

But it does not assert all the conditions necessary to prove that the intended scenario actually occurred.

At minimum, I would strengthen the assertions around the disconnect having genuinely been held, the first link having completed successfully, the second successful completion referring to a distinct handle, and the absence of unexpected additional setup commands.

### Finding D — Timer-driven behavior

The 100 ms, 300 ms and 500 ms delays are understandable for a reproducer.

They are less ideal as long-term CI dependencies, especially in heavily loaded QEMU runners.

Event-driven transitions would provide stronger determinism. If timers remain, the test should verify each prerequisite state and fail with a specific diagnostic if that state was never reached.

Conclusion for the BlueZ patch: The test is useful and has demonstrated the original bug. However, I recommend revising it before proposing it as permanent upstream test infrastructure.

### BlueZ test sequencing

Sending a known-failing BlueZ test before the required kernel fix is available to the project's CI creates noise and can make it difficult to distinguish expected failures from genuine regressions.

There is value in reviewing test code alongside the kernel change. If maintainers request simultaneous review, the test can be posted with an explicit dependency explanation.

But my default recommendation is to finish the test improvements, send the kernel series first, and submit the BlueZ test once the required kernel behavior is available in the relevant test environment.

### Hitalo Souza

I strongly recommend including Hitalo in the Cc list.

He is investigating adjacent SCO setup and teardown behavior, and his patch series has already received relevant maintainer feedback. His experience may help identify an interaction that your isolated tests missed.

There is no need to request his permission merely to Cc him on a relevant public technical discussion.

### ELL installation and permissions

The files installed under `/usr` should be audited before deletion. Confirm that they were created by the local build, are not owned by a distribution package, and are not needed by any installed binary. Then remove only the confirmed artifacts and change the build script to use a private prefix.

This cleanup does not determine the correctness of CO-02, but leaving uncontrolled build side effects in development tooling is undesirable.

I could not judge permission changes A and B because the review request does not define their intended file or directory changes.

## 10. Final recommendation

I recommend continuing with the two-patch kernel approach, subject to resolving the disconnect-worker race question.

I would not replace it with the deferred-connect prototype at this stage. Deferral may ultimately provide a better end-user experience, but it introduces a larger state-machine and lifetime problem. That deserves its own explicit RFC and review rather than being quietly folded into a small bug fix.

The existing kernel series has a meaningful independent purpose: it prevents a connection from falsely appearing established and corrects reference accounting that can disconnect an unrelated live socket.

The remaining work is worth doing because the goal is not simply to obtain acceptance. The goal is to deliver changes that future kernel maintainers can trust, understand, backport and maintain.

The current CO-02 dossier is a strong foundation for that. With the targeted refinements above, it can become a substantially more reviewer-friendly submission.
