### The reorder is more than cosmetic

Putting the ownership fix first solves a real stable-packaging problem.

V2 patch 2 had context created by the preceding `abort_reason` patch, so a tree such as 6.12—which needs the ownership fix but cannot need the `e672...` refusal fix—could not consume it directly.

V3 patch 1 now starts from untouched upstream context:

```c
link = hci_conn_link(acl, sco);
if (!link) {
        ...
}
```

and transforms that independently into the existing-link/new-link split.

That separation corresponds to the actual historical bugs:

**Patch 1:** regression created by the interaction of `06149746e720` reuse semantics and `8a5b0135d4a5`'s error-path drop.

**Patch 2:** different regression caused by `e6720779ae61`.

**Patch 3:** race-completion of patch 2 on that newer lifetime model.

So the reordered series is not merely easier to cherry-pick; it now matches the historical dependency graph better.

### Patch 1 is balanced on old and new SCO ownership models

I rechecked the subtle concern from the earlier reviews: 6.6/6.12 predate `816fb1590a4c`, so their socket ownership is not the same as current bluetooth-next.

Patch 1 is still correct there.

On the old model, when a reused SCO already has a link, the caller needs the explicit new `hci_conn_hold(sco)`. If `sco_chan_add()` returns `EBUSY`, `sco_connect()` drops exactly that new caller hold. If attachment succeeds, that hold becomes the socket's effective lifetime hold.

The redundant `hci_connect_acl()` hold is separately dropped because the already-existing parent link already owns its ACL reference.

Your 6.12 experiment validates exactly the dangerous branch: unpatched Connect Twice destroys the first connection 3/3; patch 1 changes only that case and makes it pass 3/3. That is much more useful than simply proving that the code builds.

I would therefore keep patch 1 exactly where it is now.

This is a wording nit, **not a resend-level issue**.

### The BlueZ `EBUSY` widening is acceptable

I specifically looked for whether this reopened the original weak-oracle problem.

It doesn't.

During now accepts:

```text
ECONNABORTED
EBUSY
or a genuinely newly established link
```

but it still rejects the bad behavior you discovered:

```text
connect() reports success
no second Setup Synchronous Connection exists
old Disconnection Complete kills the socket
```

An `EBUSY` result is an honest synchronous refusal, which is exactly what older pre-6.13 kernels legitimately provide. After either refusal errno, the test releases the held Disconnection Complete and still checks that there was only the original setup/completion/disconnect sequence.

Could accepting EBUSY mean a future current kernel silently changes errno from ECONNABORTED to EBUSY without failing this BlueZ test? Yes. But I don't consider that a defect in this test because the correctness contract here is **“do not report a connection that has no link,”** not “freeze this exact errno forever.” The current kernel patch itself still tests and documents ECONNABORTED.

That is a much healthier upstream test than one artificially tied to one implementation.

### The new Connect Twice teardown check is good

Previously the test established that both eventually disappeared. V3 now also verifies the relationship the lifetime model requires: the parent ACL must not disappear out from under the SCO child.

I don't see a false-pass problem in the revised logic.
