# CO-12: what a long-duration design needs (2026-11-14)

Kernel references are bluetooth-next `da3cc02587c6` unless a path says otherwise. Marks: [source] read from the code, [measured] from a test log, [inferred] my reasoning, not run.

## 1. The defect and what the clamp does
- `hci_enable_ext_advertising_sync()` (`hci_sync.c:1746-1752`) converts `adv->timeout` (seconds, `u16`, up to 65535) to milliseconds in a `u16` and then to 10 ms units for `set->duration` [source]. Wrapped values: 66 s gives Duration 46, 655 s gives 6517, multiples of 8192 s and 6357 s give 0 (no limit) [measured: base cases, 11-01 and 11-14].
- The HCI field is 16 bits in 10 ms units: at most 655.35 s [source: Core spec, LE Set Extended Advertising Enable]. No code that only changes the number sent to the controller can honour a longer MGMT timeout.
- The clamp (u32 arithmetic, `min_t(u32, duration / 10, U16_MAX)`) makes every timeout up to 655 s exact and ends longer ones at 655.35 s. It never leaves an instance without a deadline, which the wrap does for 8192 s and its multiples.

## 2. Choice for the operator
| | clamp now | design first |
|---|---|---|
| change | 3 lines in `hci_sync.c` | new timer per instance, ~60 to 100 lines in `hci_core.c`, `hci_sync.c`, `hci_core.h`, maybe `hci_event.c` [inferred] |
| behaviour above 655 s | ends at 655.35 s, not at the requested time (stated in the message) | ends at the requested time |
| risk | none for timeouts the controller can express; long requests end early | lifetime/locking of a timer on `adv_info`; needs review rounds; touches the area Cen Zhang's 14927631 rewrites |
| who is affected | MGMT clients that pass a timeout (`btmgmt add-adv -t`); bluetoothd is not (its own timer, MGMT timeout 0, per the earlier source check) | same |
| stable | trivially backportable (7.3.y to 6.1.y form exists; 5.15.y/5.10.y in `hci_request.c`) | hard to backport |
A middle course is possible: send the clamp now as a bug fix that stops the wrap and the "never ends" case, and say in the message that a host deadline is the follow-up. The message already names the three options.

## 3. What a correct long-duration design needs [source for locations, inferred for the design]
Goal: a non-mesh instance whose timeout is above 655 s ends at its requested time on an extended-advertising controller, with Advertising Removed sent, as it is today below 655 s.

1. **A deadline per instance.** The existing host expiry (`hdev->adv_instance_expire`, `hci_core.h:620`; `adv_timeout_expire()`, `hci_sync.c:575`) is one delayed work for the one instance being advertised and is armed only `if (!ext_adv_capable(hdev))` (`hci_sync.c:2224`). Extended controllers run several sets at once, so each instance needs its own. `struct adv_info` already carries a per-instance delayed work, `rpa_expired_cb` (`hci_core.h:268`), initialised in `hci_add_adv_instance()` (`hci_core.c:1804`) and cancelled in `hci_free_adv_instance()`/`hci_adv_instances_clear()` (`hci_core.c:1720`, `1761`) and in `hci_dev_close_sync()` (`hci_sync.c:6079`); a second one for the deadline fits that pattern.
2. **Arming.** In `hci_enable_ext_advertising_sync()`, where the Duration is computed: for a timeout above 655 s, either send Duration 0xffff and arm the work for the full timeout (the work then wins), or send 0 (no controller limit) and arm for the full timeout. Sending the clamp value keeps the controller as a safety net if the host work is lost, so it is preferable [inferred]. The arm must happen under `hdev->lock` where `adv` is still valid (14927631 already copies the needed fields out under the lock there).
3. **Expiry.** The work function mirrors `adv_timeout_expire()`: take `hdev->lock`, queue `adv_timeout_expire_sync()` (`hci_sync.c:557`, which calls `hci_clear_adv_instance_sync(..., force=false)` and disables advertising when the list is empty) with the instance number, not a pointer. `hci_clear_adv_instance_sync()` already sends Advertising Removed. The work must not hold `hdev->lock` across the HCI command (same rule as CO-04/CO-05).
4. **Termination event.** At 655.35 s the controller (if given 0xffff) sends LE Advertising Set Terminated; `hci_le_ext_adv_term_evt()` (`hci_event.c:6653`) removes the instance for any non-zero status. So with the 0xffff form the controller ends the set at 655.35 s and removes it first, which defeats a longer host deadline. To honour a longer timeout the controller must be told 0 (no limit) for those instances, so the controller never terminates them, and the host work is the only deadline. Safety net and exactness conflict here; the design must pick one [inferred, needs a test on real hardware or the emulator's event path].
5. **Interaction with `remaining_time`.** `adv->remaining_time` is decremented only by `hci_schedule_adv_instance_sync()` (`hci_sync.c:2220`) and the removal test `!adv->remaining_time` (`hci_sync.c:534`, `2350`) is for the legacy rotation. An extended instance never uses it. The deadline can be kept as `jiffies`/work delay only; no new field is strictly needed besides the work.
6. **Suspend and resume.** `hci_resume_advertising_sync()` re-enables every set through `hci_enable_ext_advertising_sync()`, which recomputes the Duration from the full `adv->timeout` (today also for timeouts below 655 s): a timeout restarts at each resume. A host deadline must either survive suspend or be re-armed with the time left; the current code has no remaining-time bookkeeping for extended instances, so this is a behaviour decision, not only code [source, inferred].
7. **Power off and removal.** Cancel the work in `hci_free_adv_instance()` and at power off, as `rpa_expired_cb` is; use `cancel_delayed_work_sync()` outside `hdev->lock`, since the work takes it.
8. **Mesh.** Mesh instances carry milliseconds and 1000 ms timeouts; Pauli Virtanen's `8a8d51eeedeb` fixed their conversion. They stay on the controller Duration.
9. **Capability changes.** `ext_adv_capable()` is re-read at every bring-up; an instance added when the controller reported extended advertising may be enabled when it does not (Piyus Kedia's 14976301 deals with data length for that case). The deadline must work for both the legacy rotation and the extended path, or the add path must reject/convert at add time.
10. **Tests.** The AdvDur and Add cases already pin Duration and removal time up to 655 s. A long-duration design needs an emulator that can fast-forward or a timeout the tests can reach (the Add cases cannot wait 656 s: they only read the Duration). A kprobe/trace check of the work being armed, and a case with two instances of different long timeouts, would be the minimum.

## 4. The reject option (option 2 in the message)
Validate in `add_advertising()` (`mgmt.c:9107`, `timeout` at 9137) and `add_ext_adv_params()` (`mgmt.c:9306`, 9362): if `ext_adv_capable(hdev)` and the timeout is above 655, return Invalid Parameters. Small, and the MGMT timeout then always holds. Costs: a request accepted today becomes an error; the capability can change between add and enable (item 9), so the check at add time is not airtight; `doc/mgmt.rst` documents the timeout as seconds without that limit, so BlueZ's documentation would need a line [inferred].

## 5. Interaction with Cen Zhang's 14927631 (Luiz asked for a v2 on 11-02)
- Its first patch rewrites `hci_enable_ext_advertising_sync()`: it looks the instance up under `hdev->lock`, copies `handle` and a `u16 duration` out (`duration = adv->mesh ? adv->timeout : adv->timeout * MSEC_PER_SEC`), unlocks, and uses the copy [source: posted diff]. The overflow is still there, in `u16 duration`, so that patch does not fix it and does not touch the clamp's meaning.
- **Clamp:** the clamp's hunk and its hunk overlap textually. On 11-01 both orders applied with one conflict each and gave the same tree (`co12-rework-20261101/evidence/orders-tree-compare.txt`, 14927631 on its old base) and a clamp form for on top of the series exists (`co12-rework-20261101/patches/on-series-1197214/`). Today 14927631 no longer applies even to the tip (`hci_sync.c:2077`), so I could not repeat the combination; after its v2 the clamp is a 3-line rebase either way [measured for 11-01, inferred for the v2].
- **Host-deadline design:** it would be written on top of that restructure: the arm happens in the same block where 14927631 snapshots fields under the lock, and the new work function must use an instance number, the same rule 14927631 applies to `hci_remove_advertising_sync()` and `hci_clear_adv_instance_sync()`. If 14927631 lands first the design is easier (the locking pattern exists); if the design lands first, 14927631's v2 has to cover the new work too. Luiz's request to avoid an allocation (`adv_instance_list_copy()`) also applies to any copy the design would add [source: his 11-02 reply].
- Recommendation if the operator wants the smallest risk: send the clamp now (it is orthogonal to the UAF fix; whichever lands second rebases a 3-line hunk), and leave the host deadline until 14927631's v2 settles.
