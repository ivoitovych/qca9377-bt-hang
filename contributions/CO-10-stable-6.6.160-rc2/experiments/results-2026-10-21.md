**l2cap-tester stops at the same case on both kernels.** After 96 distinct cases (103
progress lines), "L2CAP Ext-Flowctl Server - Accept 2 Close 1" reaches "Accept deferred setup"
and never finishes, on 6.6.159 and on rc2 alike. Both guests were stopped after about 12
minutes (`scripts/stop-own-process.sh`), so the cases after it did not run on either kernel.
Same place, same kernel line: a tester case newer than what 6.6 supports, not a regression.

**"Defer limit" is rc2's L2CAP fix at work.** The repeat runs
(`experiments/repeat-case.sh tmp/co10-20261021-repeat-l2cap-limit l2cap-tester limit 3`):
6.6.159 **Failed** 3/3, rc2 **Passed** 3/3. On 6.6.159 the fifth connect of the case is not
deferred ("Connect in progress, sk = 36", without "(deferred)"). rc2's `e2910b42115a`
"Bluetooth: L2CAP: fix out-of-bounds write in l2cap_ecred_connect" (upstream `56c2b5831d39`)
describes exactly that: "If 6 L2CAP sockets are connected at the same time in order DDDDND …
the last can bump the total to max+1".

**mesh-tester crashes 6.6.159; rc2 is clean.** On 6.6.159, "Mesh - Enable 2" produces:
- `BUG: KASAN: stack-out-of-bounds in set_mesh_sync+0x1a9/0x1c0`;
- then `general protection fault, probably for non-canonical address 0xdead000000000108`,
  with RIP in `mgmt_pending_remove`, a list-poison value.

The guest then hung, and was stopped after about 12 minutes.

On rc2, Enable 1 and 2, both Read Mesh Features cases and the three Send cases pass, with 0
report lines. rc2's `78504bca42ab` "Bluetooth: MGMT: fix crash in set_mesh_sync and
set_mesh_complete" (upstream `e8785404de06`) names both: "BUG: KASAN: stack-out-of-bounds in
set_mesh_sync" and "double list_del via mgmt_pending_valid + mgmt_pending_remove".

The two "Send cancel" cases time out on rc2. In this full run 6.6.159 crashed before
reaching them, so this run cannot compare them. **The isolated runs in the next section
close that gap.** (Upstream, these cases passed on the BlueZ CI bot only from 2026-10-10,
after a bluetooth-tree commit that no stable line carries; `docs/STATUS.md`, M-1.)

**Kernel reports on rc2:** 0 in every tester's log.

## Mesh, every case compared (added after the fourth outside review)

The full 6.6.159 run crashed at "Mesh - Enable 2", so the cases after it had no control
verdict. Each was then run by itself on both kernels:
- `repeat-case.sh … mesh-tester cancel 3`;
- `… Features 1`;
- `… Send 1`.

The outputs are in `tmp/co10-20261021-repeat-mesh-{cancel,features,send}/`.

| case | 6.6.159 | 6.6.160-rc2 |
|---|---|---|
| Read Mesh Features; … - Disabled | Passed; Passed | Passed; Passed |
| Send; Send - too short; Send - too long | Passed ×3 | Passed ×3 |
| Send cancel - 1 | not passed, 4/4 (Timed out 3, Failed 1 at 0.043 s) | Timed out 4/4 |
| Send cancel - 2 | Timed out 4/4 | Timed out 4/4 |

So the two "Send cancel" timeouts on rc2 are not new: neither case passes on 6.6.159 either.
`kernel-report-scan.py` finds all ten runs clean, each with the intended kernel. Every mesh
case now has a verdict on both kernels. **Apart from "Enable 2", which is rc2's mesh fix,
each case passes on both kernels or fails on both.**

The verdicts are not all identical. One 6.6.159 run of "Send cancel - 1" ended Failed (after
0.043 s) where every rc2 run timed out. That is why the mail says "either pass on both or fail
on both", not "the same verdict" (corrected in version 5, after the reviewers' recheck).
