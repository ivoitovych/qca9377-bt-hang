# Independent review: CO-10 — Linux 6.6.160-rc2

Pre-submission technical, procedural, and maintainer-experience review · 21 October 2026

## Executive assessment

Revise before sending

This is a legitimate and potentially valuable contribution to Linux stable maintenance. The underlying approach is sound: build the release candidate and its predecessor, run relevant regression tests under comparable conditions, demonstrate that two specific Bluetooth fixes behave correctly, and report the results to the stable maintainers.

The Linux stable process explicitly welcomes this kind of contribution. Test reports sent in response to release-candidate announcements, including `Tested-by` trailers, are part of the documented review process.




The important distinction is between the quality of the underlying testing and the precision of the claims made about it.

My preliminary conclusion is that the evidence for the two tested fixes is stronger than the wording of the proposed email. In particular, the statement that there are no Bluetooth regressions needs narrower language, because emulator coverage is not equivalent to validating the whole Bluetooth subsystem.

My standard for this review is whether a busy maintainer can quickly determine what was tested, on precisely which kernel, what passed or failed, what remained untested, and how much confidence the evidence deserves.

## 2. Findings that should be addressed

### Finding A — Overbroad regression claim

High priority

The draft currently says:

> No regressions in Bluetooth

This goes beyond the demonstrated evidence.

The tests exercise substantial parts of the kernel Bluetooth stack through BlueZ's emulator, but they do not establish that every Bluetooth behavior is free of regression. They also do not exercise the QCA9377 device on this release candidate.

Replace that wording with a statement such as:

> No new failures were observed in the Bluetooth emulator tests compared with 6.6.159.

This retains the positive result while identifying the observation's scope.

The distinction matters because rc2 contains many Bluetooth changes besides the project's own three. The results document identifies 41 commits touching Bluetooth-related paths between the two kernel revisions. An unchanged test verdict is useful evidence, not proof that every one of those changes is harmless.

### Finding B — The 43 existing nonpassing cases should be disclosed

High priority

The draft gives the 508-case total and says the outcomes are unchanged except for the fixed race. Technically, this is consistent with the results document.

However, the new kernel still has 37 failures and six timeouts in `mgmt-tester`.

These are important facts. A maintainer should not have to open the repository to discover them.

I recommend stating the counts and explaining that the same 43 cases have identical nonpassing verdicts in the control. This makes the report more credible, not less.

In fact, comparing failing-test identities rather than just pass totals is one of the strongest aspects of the work. Make that visible.

### Finding C — The extended test suite is unfinished in the published record

Must resolve before sending

The published draft still contains `[PENDING]`, and the results document still has a placeholder for ten additional tester suites.

The suite selection itself appears appropriate. I compared the list in [all-testers.sh](https://github.com/ivoitovych/qca9377-bt-hang/blob/main/contributions/CO-10-stable-6.6.160-rc2/experiments/all-testers.sh) against published BlueZ CI reports: the eleven `TestRunner_*` suites, including `mgmt-tester`, align with the CI job list.




The critical requirement is that the comparison must finish and its results must be checked before making the corresponding claim.

If the other suites reveal differences, particularly failures in ISO, L2CAP, RFCOMM, or mesh, they should be investigated or explicitly reported. A differing verdict does not automatically establish a regression, because emulator tests can be flaky.

Do not delay reporting the completed, relevant tests solely to obtain an unbounded testing result. If necessary, send an accurately scoped report covering only the completed tests, without the pending line.

### Finding D — The test harness can mask execution failures

Medium priority

I inspected the two shell scripts and the Python comparison tool. There is a concrete test-infrastructure weakness worth correcting.

In `build-and-test.sh`, the `run()` function executes the QEMU test under `timeout`, prints its exit status, and continues. The script does not automatically reject an unexpected exit, a guest boot failure, or incomplete test output.

`all-testers.sh` behaves similarly. This is not necessarily wrong, since some existing BlueZ suites legitimately exit nonzero because of known failing tests. However, the harness must distinguish an expected nonzero test verdict from a failure to execute the test successfully.

The Python comparator also has two limitations:

- Repeated test names overwrite previous entries in its dictionary.
- A missing, truncated, or unparseable test log is not explicitly rejected through a required case count or completeness check.

Neither demonstrates that the reported 508-case comparison is invalid. That comparison has the expected number of cases and a sensible result.

Nevertheless, these are avoidable weaknesses in a test pipeline intended to support upstream evidence.

The appropriate improvement is not to require every suite to exit zero. Instead, record each runner's exit status, validate that the expected test inventory was parsed, detect duplicate names, and fail the comparison when inputs are incomplete.

### Finding E — The raw evidence and build environment are not fully reproducible from the public dossier

Medium priority

The public evidence is reasonably well organized, but the description promises more independent reproducibility than currently exists.

The build invokes `tmp/mesh-tester-ci/build.mk` and a QEMU wrapper under `tmp/`. These are local, non-public inputs. Likewise, the raw test logs and checksums remain on the development host.

The project documents the kernel image hashes, compiler version, source versions and commands, which is good. But a reviewer cannot independently verify the full construction or all of the output from the public materials.

The best improvement is a compact, sanitized evidence package containing the exact build recipe or relevant build configuration, final `.config` checksums, test-case summary, runner exit codes, and decisive excerpts from the two regression tests.

Publishing enormous logs is unnecessary for the upstream email. Keeping them locally with hashes is reasonable; publishing enough evidence to check the important claims is better.

There is also a simple configuration verification worth adding: ensure the actual generated kernel configurations enabled KASAN and lockdep on both builds, rather than inferring this solely from the requested configuration fragments.

### Finding F — Kernel diagnostics should be described exactly

Medium priority

The draft reports no KASAN or lockdep findings. The test-runner source does configure guest console output to expose warnings, so inspecting those logs is a meaningful check.

However, the present searches cover selected patterns, not all possible kernel diagnostics. They do not comprehensively cover all oops, panic, RCU stall, UBSAN, and related error strings.

A wider scan of the existing logs is inexpensive and worthwhile. The resulting email should preferably say that no kernel warnings or sanitizer reports were observed in the captured test logs, rather than imply that no problems could exist.

### Finding G — Be explicit about the QCA9377 limitation

Medium priority

The [review request](https://github.com/ivoitovych/qca9377-bt-hang/blob/main/contributions/CO-10-stable-6.6.160-rc2/REVIEW-REQUEST.md) asks whether the hardware limitation should be omitted or disclosed.

I recommend disclosing it in one short sentence.

The USB device-table patch is present in rc2, but the physical QCA9377 has not been exercised under the tested 6.6 kernel. The earlier test of the same device-table entry on your Ubuntu kernel is meaningful evidence for that entry, but it is not a hardware test of this particular release candidate.

An appropriate formulation is:

> Testing used emulated Bluetooth controllers; no physical Bluetooth hardware was tested with rc2.

This does not weaken the `Tested-by` tag. Kernel documentation says that the tag represents successful testing in a particular environment, not universal validation of every hardware configuration.

I would not reboot the laptop into an unfamiliar kernel merely to strengthen this report. The additional risk is unnecessary for a correctly scoped emulator test submission.

### Finding H — Email threading and provenance

The reply format is appropriate. The proposed subject, quotation of the announcement, and final `Tested-by` trailer are consistent with stable-list practice.

However, the public repository deliberately omits the sendable email headers. Consequently, I cannot verify the actual `Message-ID`, `In-Reply-To`, `References`, `To`, or `Cc` values.

Before sending, these should be verified directly against Greg's original announcement. A proper reply-all is reasonable; manually guessing or reconstructing the recipients is not.

The `Tested-by` name and email in the draft agree with the identity documented for your earlier stable submissions. No `Signed-off-by` trailer is required for a standalone testing report.

### Finding I — Causal attribution and the experiment's limits

One additional distinction matters scientifically.

The comparison between 6.6.159 and 6.6.160-rc2 tests an entire release candidate against its predecessor, rather than changing only one Bluetooth patch at a time.

Therefore, strictly speaking, these new runs demonstrate that the two target problems occur in the older release and do not occur in the new release under the tested conditions.

The earlier project experiments, including patch-specific tests with and without the BT-9 backport, provide stronger isolation of the individual fixes. Together, those two lines of evidence are persuasive.

There is no need to include that whole argument in the upstream reply. But the public dossier could briefly connect the release-candidate validation to the earlier isolated experiments.

## 6. Will this help the maintainers?

Yes, provided that its claims remain precise.

The value of a release-candidate test report is not measured by whether it discovers another defect. Confirming that an existing fix works in an older stable kernel, while finding no new failures in a relevant test environment, is itself useful.

CO-10 also has three qualities that make it more valuable than a routine smoke-test response.

First, it provides a concrete baseline comparison rather than reporting only success on the new kernel.

Second, it supplies tests with specific failure oracles. The BT-9 test checks the discovery race; the BT-8 reproducer checks a particular MGMT response status. These are understandable results rather than a collection of opaque log messages.

Third, the experiments are attached to an existing contribution history, including accepted upstream fixes and regression tests. That gives the work technical continuity.

There is a corresponding obligation: the reported scope must be narrow enough that the maintainer does not have to investigate what the tester actually meant.

An accurate two-paragraph test report creates very little triage burden. An overconfident report saying that the entire subsystem has no regressions could do the opposite.

I would also distinguish two meanings of top quality. For the public research dossier, achieving top quality means reproducibility, precise source versions, independently checkable evidence, and proper handling of incomplete results. For the upstream mailing-list reply, top quality means something different: maximum useful information with minimum reading and interpretation burden.

Your project should keep the detailed dossier. The stable maintainers should receive the concise, verified conclusion.

My recommendation: proceed with CO-10 after the P0 checks, with the revised wording. If the extended suites are incomplete near the upstream deadline, report only the completed tests rather than making an unsupported claim or missing the opportunity entirely.
