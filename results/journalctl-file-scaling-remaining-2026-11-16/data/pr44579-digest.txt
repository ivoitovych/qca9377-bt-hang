== PR body ==
reading the journal looks at every journal file for every single entry, even tho only the file we just read from has anything new, and with rotated files that one nearly always wins again. so the more files you have, the slower every read gets.

```
journalctl -o cat            before   after
real journal, 100 files      6.2s     3.5s
1M entries, 100 rotated      0.7s     0.27s
1M entries, 1000 rotated     6.3s     0.30s
1M entries, 100 interleaved  0.87s    0.88s
```

the full scan now also remembers the runner-up. if the winner's next entry still comes before it, there's no need to look at the other files. anything else falls back to the full scan, which still runs at least once a second so new entries get picked up. the runner-up is only tracked once a file has won twice in a row, so interleaved journals don't pay for it.

one tradeoff: when following the journal (`-f`), the shortcut is off while a file that isn't archived has run out of entries, because it could still get a new one that sorts earlier. plain `journalctl` opens the journal as immutable, so it keeps the shortcut either way.

for the original version i compared old and new output byte for byte and ran seeded random walks, about 10M entries in total, all identicall. after the review fixes i re-ran the journal tests, compared output on the real journal (plain, `-p err`, `-r -u`) and a 1000 file journal, and re-timed those two (3.5s and 0.25s). the table is from before the fixes. added a test for a new entry showing up in a file that was already at the end, it fails without the fix.
