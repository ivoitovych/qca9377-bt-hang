2. INSTALL (takes effect at the next cold boot only)
----------------------------------------------------
  scripts/module-updates.sh --krel 7.0.0-42-generic --module bluetooth install $P/bluetooth.ko --trial-open-ok
  scripts/module-updates.sh --krel 7.0.0-42-generic --module btusb install $P/btusb.ko --trial-open-ok
      (leave --trial-open-ok off if no trial is open)
  scripts/module-updates.sh --krel 7.0.0-42-generic --module bluetooth status
  scripts/module-updates.sh --krel 7.0.0-42-generic --module btusb status
      -> "next boot resolves: /lib/modules/7.0.0-42-generic/updates/bluetooth.ko" and ".../updates/btusb.ko",
         srcversions FD8499CD70E95ED232382C7 and (B) 77C6DA8755DAE33C432E1AD / (A) B5429902B72BE93C6DFA4CB.
  The two modules are a matched pair for the symbol CRCs only; the struct hci_conn layout is unchanged (the air mode
  is kept in the byte "sid", see the report), so rfcomm, bnep, hidp and the other dependants stay the stock ones and
  still load. Install BOTH or neither: btusb.ko of either pair reads the byte that only the new bluetooth.ko
  writes (the stock one leaves it at 0xff), so with the stock bluetooth.ko it would see no SCO link up and keep
  alternate setting 0 (inferred from the code, not run). The reverse, new bluetooth.ko with E3's btusb, is harmless.

------------

5. THE TEST (mark each step's clock time; times as HH:MM:SS)
-----------------------------------------------------------
  Terminal A (read-only watcher, one line each time interface 1's alternate setting changes):
    /root/exp/agent-work/laptop-btusb-modules-20261111/scripts/alt-watch.sh 13d3 3503 3000 | tee /root/co21-alt-watch.txt
  Terminal B (kernel lines):
    journalctl -k -f --grep 'set USB alt|corrupted SCO|unknown handle|closed handle|unknown connection handle'
  Reading the alternate setting: 0 = no isochronous bandwidth. One transparent (mSBC) link: 1. One CVSD link: 2;
  two CVSD links: 4. (Two mSBC links: still 1.) The watcher samples once a second.

  T1 the main case (CO-21's two-link defect): connect both headsets in the hands-free profile; start a stream that
     makes each one open its call link (for example a recording per headset:
     `wpctl status` for the headset input node ids, then `pw-record --target <id> /tmp/hsA.wav` and
     `pw-record --target <id> /tmp/hsB.wav` in two shells; how WirePlumber opens the links is inferred, not
     measured here). Watch terminal A: first link -> 1 (mSBC) or 2 (CVSD); second link -> 1 or 4.
     Then hang up ONE headset (stop its recording or disconnect it). Wait 5 s.
        PASS: terminal A shows no 0 while the other link is up (back to 1 for mSBC, 2 for CVSD), and the other
              recording's file keeps growing with sound.
        FAIL: terminal A shows "bAlternateSetting 0" while the other call is still up, and that recording goes silent
              or stops growing. (This is exactly what the stock module does; reproduced in a guest, see the report.)
     Repeat, hanging up the other headset first, 3 times in all.
  T2 the single-link race: with headset A idle, start A's call link and, within about a second, connect or disconnect
     headset B (or any other Bluetooth device). 10 tries.
        PASS: after each link is up, terminal A shows 1 (mSBC) or 2 (CVSD), never 0, within about 2 s.
        FAIL: "bAlternateSetting 0" while a call link is up and silent.
        (Hard to hit on purpose: the stock records say "281 pending setups over 68 boots, no link ever ran on alt 0",
         so a PASS here is weak evidence; a FAIL is decisive.)
  T3 (pair-B only, CO-20): several normal hang-ups. Expect: "corrupted SCO packet" no longer at each hang-up;
     new lines, if anything, are "SCO packet for unknown handle N dropped" (rate-limited, error level). The
     debug-level line for data of the link just closed ("SCO packet for closed handle N dropped") is hidden unless
     enabled. That switch is a dynamic-debug flag, not a module change; your call whether to use it:
       echo 'format "SCO packet for closed handle" +p' > /sys/kernel/debug/dynamic_debug/control
     Any "no memory for SCO packet" line is a real allocation failure.
     A pair-A boot keeps the old "corrupted SCO packet" lines: they are the baseline of CO-20.

6. WHAT TO READ AFTERWARDS (read-only; note the boot's start time as "YYYY-MM-DD HH:MM:SS")
------------------------------------------------------------------------------------------
  journalctl -k -b 0 --grep 'set USB alt|corrupted SCO|unknown handle|closed handle|unknown connection handle'
     PASS: no "set USB alt:(N) failed!" line. (CO-21 itself writes no log line: the evidence is terminal A.)
     CO-20 on pair-B: compare the count of "corrupted SCO packet" with the number of hang-ups.
  scripts/sco-ledger.sh 0
     PASS: one row per link; every row "hangup-ok"; totals "timeouts 0". For the link that stayed up while the other
           hung up: "alt-1 27-byte buffers" keeps growing after the other's hang-up (mSBC), seconds streamed run
           to its own hang-up. FAIL: any TIMEOUT 0x0406, or a stayed-up mSBC link whose buffers stop at the other's
           hang-up (that is the defect as the ledger sees it).
  python3 -I scripts/sco-link-closure.py --from "YYYY-MM-DD HH:MM:SS" /var/log/bt-health/capture
     PASS: every link closed, Disconnection Complete status 0x00, no failed setups you did not cause, nothing open at the end.
  cp /root/co21-alt-watch.txt (keep it with the ledger output)
