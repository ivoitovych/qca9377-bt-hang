## T2. `scripts/ci-local.sh`: the bot's checks, twice, with a baseline diff

**What it does.** `scripts/ci-local.sh [options] <patch>…` takes a BlueZ tree
(`cache/bluez`, `origin/master`) and the patch files in series order, makes a detached
worktree at the base with ELL beside it, and runs the bot's recipes of §T1: `pre-ci_am`
(`git am`), CheckPatch (the image's `checkpatch.pl`, inside the tree), GitLint (the bot's
gitlint file, patchwork-style name + body), BuildEll, then — on the base and again after
`git am` — BluezMake, bluezmakeextell, CheckSmatch and ScanBuild, with IncrementalBuild
(`git am` + `make` per patch) in between. The two sides' diagnostics are compared with
line and column numbers removed (a patch that inserts lines above an old warning moves it,
and a moved warning is not a new one) and every line is classed **NEW** (only with the
patches), **PRE-EXISTING** (both), **FIXED** (only on the base); a check with no line on
either side is **PASS**. For CheckSmatch the script also prints what the bot would post:
every smatch line on a file the series touches. The base side is cached per base commit
(`tmp/ci-local/base-cache/`) so a second series on the same master costs only its own
side. `--functional --kernel-image <bzImage>` adds TestFunctional; `--kernel` switches to
the kernel bot's check set (see the kernel runs below). Exit status 1 only on a NEW
finding. Everything the bot does with its tokens (patchwork, GitHub, mail) is left out.

**Differences from the bot, stated:** (1) the bot posts the CheckSmatch lines of touched
files without looking at the base; the script shows both views. (2) The bot's committer is
its GitHub actor; here `git am` commits as this checkout's identity, which is what
VerifySignedoff then sees. (3) The bot runs on Ubuntu 26.04 with clang-tools 21 and GCC
of that release; this container is Ubuntu 24.04 with clang-tools 18 and GCC 14, so
compiler and scan-build wording can differ; smatch, sparse, gitlint and checkpatch are the
bot's versions (§T1). (4) No `/dev/kvm` here (TestFunctional, §T3).

### Can the harness run here?

`/dev/kvm` is absent (`ls -la /dev/kvm`: `No such file or directory`). The harness
launches every VM through BlueZ's `tools/test-runner`, whose QEMU machine line is
`type=q35,accel=kvm:tcg` (`tools/test-runner.c:856`): without KVM, QEMU falls back to
TCG, software emulation. So the suite can run here, slowly and with timings that are not
the bot's; a rate measured under TCG is a rate of this container, not of the bot's runner
(4 vCPUs with KVM). The bot's TestFunctional job took 830 to 1235 s per series on
2026-10-10.

A first attempt with the harness as installed failed in setup on all 10 runs,
`RuntimeError: Process exited unexpectedly`, because `pytest_bluezenv/env.py:823` always
passes test-runner's `-H` (`--qemu-host-cpu`, "requires KVM support") and QEMU answers
`CPU model 'host' requires KVM or HVF`. For the runs below the installed copy of the
harness (the venv, not BlueZ) was changed to pass `-H` only when `/dev/kvm` exists; the
emulator testers (§T4) use test-runner without `-H` and ran unchanged. Also installed for
the guests: `chronyd` (the harness warns when it is missing), `qemu-system-x86` 8.2.2;
Ubuntu 24.04's `virtiofsd` 1.10 refuses test-runner's `--readonly` and was removed, so the
guests mount the host root over 9p (test-runner's fallback).

**The reproduction did not happen: the harness cannot run in this container.** With the
host-CPU flag out of the way the guests boot (about 10 s to the init under TCG) and the
harness's agent connects after about 75 s, but every run fails in setup before the test
body, on both attempts
([`functional-pair_bredr-hostcpu/`](ci-local-2026-10-10/functional-pair_bredr-hostcpu/):
the harness as installed, 10 of 10 runs `Process exited unexpectedly`, the `-H` failure
above; [`functional-pair_bredr-60s/`](ci-local-2026-10-10/functional-pair_bredr-60s/):
without `-H`, the bot's `--vm-timeout 60`, 3 of 3 runs `RemoteTimeoutError: Failed to
establish connection` after 60 s, the loop stopped there;
[`functional-pair_bredr-diag-300s/`](ci-local-2026-10-10/functional-pair_bredr-diag-300s/)
with `--vm-timeout 300`, `RemoteError: load failed`). The guest log says why, the same
lines in every guest of every run:

```
Attaching BR/EDR controller to /dev/hvc1
Bluetooth: hci0: command 0x1001 tx timeout
Bluetooth: hci0: Reading local version information failed (-110)
Set Powered for hci0 failed with status 0x11 (Invalid Index)
```

The functional harness gives each guest its emulated controller from a `btvirt --server`
on the host, attached to the guest over a virtio console (`/dev/hvc1`); that controller
never answers the kernel's first command, so `hci0` is unregistered again and bluetoothd's
plugin reports `load failed`. The emulator testers of §T4 take their controllers from
`hci_vhci` inside the guest and ran fine on the same kernel and QEMU, which puts the fault
on the host side or the serial path, not in the guest kernel or the harness.

**The cause, found 2026-10-11 15:18:00 to 15:20:00 UTC — CONFIRMED, and it is not TCG.** This
section first blamed software emulation, which was the visible difference from the bot
and was never probed; the probe took two minutes
([`harness-diag/`](ci-local-2026-10-10/harness-diag/)). A host-side `btvirt --server` was
started by hand and sent an H4 `Read Local Version Information` (`01 01 10 00`) over each
of its sockets (`probe2.sh`, `probe2.out`):

| socket | btdev type | answer |
|---|---|---|
| `bt-server-bredr` | BR/EDR only, no crypto | Command Complete in 1 ms: `04 0e 0c 01 01 10 00 05 00 00 05 f1 05 00 00` |
| `bt-server-bredrle` (the one the harness uses) | BR/EDR + LE | connection dropped on the first byte (`Broken pipe`; `probe.sh`: `Connection reset by peer`) |
| `bt-server-le` | LE | connection dropped the same way |

`btvirt.log` shows `Request for … bt-server-bredrle` and nothing else: in
`emulator/server.c:300` the accept callback calls `btdev_create()`, which for every LE-capable
type calls `bt_crypto_new()` (`emulator/btdev.c:8353`), and on failure closes the client
without a message. `bt_crypto_new()` (`src/shared/crypto.c`) opens `AF_ALG` sockets, and this
container's kernel (`6.18.44-fc-v114`, `/proc/config.gz`) has none of
`CONFIG_CRYPTO_USER_API_HASH` / `_SKCIPHER` (`host-kernel-config-crypto-user-api.txt`;
`socket(AF_ALG, …)`: `Address family not supported by protocol`). The guest kernel built from
`doc/tester.config` has both (`guest-kernel-config-crypto-user-api.txt`), which is why the

## T4. The smatch VLA at `emulator/btdev.c:479`

**The line.** `emulator/btdev.c:479`, in `send_cmd()`:
`struct iovec iov2[2 + iovlen];` — present in BlueZ master `7428ca2df` and untouched by

rule (§T1: CheckSmatch posts every smatch line on a touched file, base or not) and by
`ci-local.sh` (§T2, where the base run shows the same line).

**Would a removal be welcome?** CONFIRMED by precedent: `1b9a0eca8` "gatt-server: Fix
integer overflow and 3 CI VLA wanings" (author date 2026-08-21, committed 2026-09-10),
whose message says "Fix CI warnings: Variable length array is used, use malloc/free

ordinary BlueZ housekeeping.

**The patch:** [`patches/bluez/btdev-vla/0001-emulator-Avoid-variable-length-array-in-send_cmd.patch`](../patches/bluez/btdev-vla/)
— not sent. `send_cmd()` has two callers, `cmd_complete()` with two iovec entries and

the array. No behaviour changes for the callers that exist. `malloc()` as in `1b9a0eca8`
would add a failure path to the emulator's hottest send function for a bound that is a
compile-time constant; a fixed array is the smaller change.
