## T2. `scripts/ci-local.sh`: the bot's checks, twice, with a baseline diff

**What it does.** `scripts/ci-local.sh [options] <patch>…` takes a BlueZ tree
(`cache/bluez`, `origin/master`) and the patch files in series order, makes a detached
worktree at the base with ELL beside it, and runs the bot's recipes of §T1: `pre-ci_am`
(`git am`), CheckPatch (the image's `checkpatch.pl`, inside the tree), GitLint (the bot's
gitlint file, patchwork-style name + body), BuildEll, then — on the base and again after
`git am` — BluezMake, bluezmakeextell, CheckSmatch and ScanBuild, with IncrementalBuild
(`git am` + `make` per patch) in between. The two sides' diagnostics are compared with
line and column numbers removed (a patch that inserts lines above an old warning moves it,
and a moved warning is not a new one) and every line is classed **NEW** (only with the
patches), **PRE-EXISTING** (both), **FIXED** (only on the base); a check with no line on
either side is **PASS**. For CheckSmatch the script also prints what the bot would post:
every smatch line on a file the series touches. The base side is cached per base commit
(`tmp/ci-local/base-cache/`) so a second series on the same master costs only its own
side. `--functional --kernel-image <bzImage>` adds TestFunctional; `--kernel` switches to
the kernel bot's check set (see the kernel runs below). Exit status 1 only on a NEW
finding. Everything the bot does with its tokens (patchwork, GitHub, mail) is left out.

**Differences from the bot, stated:** (1) the bot posts the CheckSmatch lines of touched
files without looking at the base; the script shows both views. (2) The bot's committer is
its GitHub actor; here `git am` commits as this checkout's identity, which is what
VerifySignedoff then sees. (3) The bot runs on Ubuntu 26.04 with clang-tools 21 and GCC
of that release; this container is Ubuntu 24.04 with clang-tools 18 and GCC 14, so
compiler and scan-build wording can differ; smatch, sparse, gitlint and checkpatch are the
bot's versions (§T1). (4) No `/dev/kvm` here (TestFunctional, §T3).

## T4. The smatch VLA at `emulator/btdev.c:479`

**The line.** `emulator/btdev.c:479`, in `send_cmd()`:
`struct iovec iov2[2 + iovlen];` — present in BlueZ master `7428ca2df` and untouched by
our patches (the leak fix edits `btdev_destroy()` at line 8424 onward; patch 1/3 appends
`btdev_send_event()` at the end of the file). CONFIRMED PRE-EXISTING by the bot's own
rule (§T1: CheckSmatch posts every smatch line on a touched file, base or not) and by
`ci-local.sh` (§T2, where the base run shows the same line).

**Would a removal be welcome?** CONFIRMED by precedent: `1b9a0eca8` "gatt-server: Fix
integer overflow and 3 CI VLA wanings" (author date 2026-08-21, committed 2026-09-10),
whose message says "Fix CI warnings: Variable length array is used, use malloc/free
instead." — three `uint8_t rsp_pdu[mtu]` arrays replaced by `malloc()`/`free()`. On
patchwork (series 14705742 → 14760170 → 14761186, v1 to v3) the only comments are the
bot's; no human objected and the maintainer applied v3. Earlier, `86e7b3e76` (2021) fixed
the flexible-array declarations in `lib/hci.h` for GCC 10. The other smatch cleanups in the
log (`afb47b13c input`, `c18e3bf92 shared/gatt-client`, `4bdd7090f mesh`, `3818b99c7
shared/shell`) are the maintainer's own. So a one-line VLA removal prompted by the CI is
ordinary BlueZ housekeeping.

**The patch:** [`patches/bluez/btdev-vla/0001-emulator-Avoid-variable-length-array-in-send_cmd.patch`](../patches/bluez/btdev-vla/)
— not sent. `send_cmd()` has two callers, `cmd_complete()` with two iovec entries and
`cmd_status()` with one, so the array becomes `struct iovec iov2[2 + SEND_CMD_IOV_MAX]`
with `SEND_CMD_IOV_MAX` 2, and a call with more entries returns instead of writing past
the array. No behaviour changes for the callers that exist. `malloc()` as in `1b9a0eca8`
would add a failure path to the emulator's hottest send function for a bound that is a
compile-time constant; a fixed array is the smaller change.
