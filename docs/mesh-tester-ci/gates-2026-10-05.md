## Gate 1 — I12, advertising-list locking

### The requirement and the call sites (quoted, bluetooth-next/master `036d4119079a`)

- `net/bluetooth/hci_core.c:1673-1674`: `/* This function requires the caller holds hdev->lock */`
  / `struct adv_info *hci_add_adv_instance(struct hci_dev *hdev, u8 instance,`. The same comment
  stands over `hci_remove_adv_instance()` (1606) and `hci_adv_instances_clear()` (1643). Inside:
  `list_add(&adv->list, &hdev->adv_instances); hdev->adv_instance_cnt++;` (1708-1709).
- **Unlocked caller:** `mgmt.c:mesh_send_sync:2328-2380` runs as a cmd_sync work function and
  calls `adv = hci_add_adv_instance(hdev, instance, 0, …, mesh_tx->handle);` at 2342-2349; the

### (b) Is it reachable as a real race? (quoted, then inferred)

**Result (b).**
- **Shown (quoted):** on plain bluetooth-next and on v3 + cleanup, with two CPUs or more, the
  worker's `mesh_send_sync()` path and the `add_advertising()` system call access
  `hdev->adv_instances` and neighbouring `hdev` fields at the same time, one side under
  `hdev->lock` and the other without it — including the list walk inside `mesh_send_sync()`'s own
  `hci_add_adv_instance()` running while `add_advertising()`'s `hci_add_adv_instance()` publishes a
  new list entry (smp-6, "value changed"). KCSAN reported such a race in 9 of 30 SMP boots.
- **Not shown:** corruption, a use-after-free, a wrong list state or a hang. KASAN (10 SMP + 6 UP
  boots) reported nothing; Read Advertising Features and Read Mesh Features were as expected after
  all 104 cases. Absence of a report is "not shown", not "safe". On the uniprocessor bot config
  nothing was reported at all (12 boots).
- **Inferred, worth stating to the series:**
  - The racing readers in the reports (`hci_set_adv_instance_data`, `hci_find_adv_instance` under
    `hci_schedule_adv_instance_sync`, `hci_adv_instance_flags` under `eir_create_adv_data`) are
    generic hci_sync advertising helpers. Add Advertising's own sync work calls the same scheduler
    from the worker (quoted: `mgmt.c:add_advertising_sync:9014` `return
    hci_schedule_adv_instance_sync(hdev, cp->instance, true);`, no lock in 9009-9015); so the
    unlocked-reader class is wider than mesh. Not tested without mesh.
  - On bluetooth-next the mesh instance, once added, is never removed (`STATE-MACHINE.md` I7), so
    `mesh_send_sync()`'s unlocked `list_add` + `adv_instance_cnt++` happens on the first start

    transmission, so **every** v3 start does the unlocked `list_add` — writer against writer with
    a concurrent Add Advertising, not only reader against writer. The race above is therefore
    more exposed under v3, not less.
  - v3 2/5's own tear-down reads the list without the lock: `mesh_send_done_sync()` →
    `hci_remove_advertising_sync()` → `hci_find_adv_instance()` (quoted, v3 smp-8), before
    `hci_remove_adv_sync()` takes the lock.

## Gate 2 — the unregister lock-order hypothesis

### Why the existing cases cannot reach it (quoted code, inferred mechanism)

- At unregister, `hci_unregister_dev()` sets `HCI_UNREGISTER` under `unregister_lock`
  (`hci_core.c:2670-2672`) and later calls `hci_cmd_sync_clear()` (2690) before `hci_dev_do_close()`
  (2694). `hci_cmd_sync_clear()` (`hci_sync.c:661-674`) cancels the running request, waits for
  the worker, then `mutex_lock(&hdev->cmd_sync_work_lock)` and calls every queued entry's
  `destroy(hdev, data, -ECANCELED)` (`_hci_cmd_sync_cancel_entry`, 650-659).
  `hci_cmd_sync_submit()` takes `unregister_lock` (720) and then `cmd_sync_work_lock` (735).
- On bluetooth-next the tear-down entry is `hci_cmd_sync_queue(hdev, mesh_send_done_sync, NULL,
  mesh_next)` (`mgmt.c:mesh_send_done:1137`), and `mesh_next()` ignores `err` and calls
  `hci_cmd_sync_queue()` for the head (1113-1127).
- For that destroy to run under `cmd_sync_work_lock`, the tear-down entry must be **queued and not
  yet taken** when the clear runs. Inferred: `mesh_send_done()` and `hci_cmd_sync_work()` both run
  on `hdev->req_workqueue`, which is ordered (`hci_core.c:2586 hdev->req_workqueue =
  alloc_ordered_workqueue(…)`), so the entry can only be queued while the worker is idle, and the
  worker then takes it next. The window is between `mesh_send_done()`'s submit and the worker's
  next `HCI_UNREGISTER` test (`hci_sync.c:316`). The phase-5 "held tear-down" cases hold a
  command of an entry that is **running** (on bluetooth-next: request 2's start; the tear-down
  has no HCI command there), so its destroy runs from the worker under `req_lock`, not from the
  clear.

**Result (Gate 2).**
- **Reported (quoted):** on bluetooth-next, when a mesh tear-down entry is still queued at device
  removal, lockdep reports exactly the inversion the document inferred —
  `cmd_sync_work_lock` (held by `hci_cmd_sync_clear()`) → `unregister_lock` (taken by
  `hci_cmd_sync_submit()` from the destroy callback `mesh_next(-ECANCELED)`), against the
  established `unregister_lock` → `cmd_sync_work_lock` of every submit. 16 of 16 widened boots,
  legacy and extended.
- **How it was reached:** only with the scratch delay. In 30 natural case-runs per kernel (six
  unregister cases × 5 boots, + the try boot on bluetooth-next) the tear-down entry had always run
  before the clear (`done_sync 6`, `mesh_next(err=-125) 0`), and lockdep stayed silent; the path
  was **not** reached naturally. That the window exists without the delay is inferred from the
  code (§ above), not shown. The delay changes only when the worker gets to the entry, not which
  code runs or which locks are taken.
- **Not a deadlock in these runs (quoted):** `submit_ret … ret=-19` every time — the submit sees
  `HCI_UNREGISTER` and returns; the removal completed in every boot. The document's "not a
  reachable deadlock once `HCI_UNREGISTER` is set" stands (inferred: the flag is set under
  `unregister_lock` before the clear). Lockdep reports the order anyway, once per boot, and turns
  itself off afterwards (inferred from lockdep's behaviour; consistent with one report per boot).
- **Series v3 + cleanup: silent, and the path is absent (quoted):** the same widened sequence
  queues the tear-down (`teardown submits 1`) and the clear runs, but nothing is called from it —
  v3 1/5 gives the tear-down entry a `NULL` destroy. The cost is the one the document already
  records (I6): what was on `mesh_pending` is neither completed nor freed by that path.

**What this changes for the core series.** Both findings of the design document are now facts,
not inferences, and both cut across the series rather than through it. I12 is real and is not a
mesh peculiarity: the advertising-instance helpers documented as "requires hdev->lock" are called
from the cmd_sync worker without it by mesh, ISO broadcast, LE-off and the advertising timeout,
and the list does see concurrent access from a locked system call. The series cannot be designed
on the assumption that the worker owns the list; and v3 as it stands makes the mesh side worse
(every start now adds the instance unlocked, and 2/5's tear-down reads the list unlocked). The
core redesign should take `hdev->lock` around the mesh instance's add/remove and the list walks
in `mesh_send_sync()`/`mesh_send_done_sync()` (respecting the established `req_lock → hdev->lock`
order and never holding it across an HCI command), keep the other three callers as a separate,
subsystem-wide question for the maintainers, and carry a lockdep-assert proof like gate 1a as its
own test. For unregister, v3's `NULL` tear-down destroy already removes the inversion that
mainline has; the argument for it can now cite a lockdep report instead of an inference, while the
missing drain policy (I6) remains the open design question for maintainer direction, as the
review's gate order says.
